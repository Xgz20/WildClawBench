## 2. 计算与判定口径


1. 统计Q3业务发生时间，区域销售事件event_id是应入账唯一键。HZero实际入账按入账ID计数及金额；执行成功次数不是入账次数。所有日志sheet有效，example.invalid为虚构地址，不调用接口，不需查现实产品配置。

2. 应入账金额来自区域业务事件，实际金额来自HZero实际入账。差额=实际-应入账。逐事件关联发送ID→执行ID→入账ID及已处理ID表，识别因首发响应超时导致30秒后重发的情形；幂等检查和已处理表共同支持是否跳过。

3. 差异分三类：同event_id存在两条或以上实际入账为重复入账；有Invalid payload且未入账为报文格式不合法被丢弃；其他应入账而未入账为漏推（包含未发送、签名失败、URL不一致、工作流未启用等）。其他正常或安全重试标一致。三类按上述顺序互斥。本题无金额改写、部分入账或冲正场景。

4. 原因需有字段级证据：签名失败看签名头及Invalid signature；URL错误看发送目标与有效配置URL；停用看当次执行状态；无发送以业务事件存在且完整发送表缺该ID支持。无法确定的根因保留待查，不把缺失签名头等同于全部签名错误。

5. 按区域计算应入账、实际入账、差额及三类贡献；重复贡献为实际-应入账，漏推和格式丢弃为-应入账，安全重试为0。各类别贡献和必须与总差额一致。列出全部执行成功次数>1的事件，并分别说明实际入账次数和幂等结果。


## 3. 结果工作簿


将完整结果保存为 `/tmp_workspace/results/Webhook销售对账.xlsx`。下列sheet与表头作为复核接口；允许增加字段、说明或图表，行列顺序不影响验收。可用数值或带有效缓存的公式，数值显示精度不能改变底层含义。


- **区域差额**：区域、应入账、实际入账、差额、重复贡献、漏推贡献、格式丢弃贡献。

- **事件核对**：event_id、区域、应入账、实际入账、入账次数、执行成功次数、差额、差异类别、原因、发送ID集合、执行ID集合、入账ID集合、来源。

- **成功重试**：event_id、执行成功次数、入账次数、首发响应、重试秒数、已处理ID存在、结论。


缺失数值留空或明确标“未知”，不得以0代替。来源使用“文件名|sheet名|A起始行:末列结束行”，多个实际来源以分号分隔，顺序不限。来源应指向输入中的真实行；分析明细可追加复核所需字段。数值容差：人民币金额0.01元，其余指标1e-5（记录数、ID及状态须精确）；统计结果建议保留6位有效数字。若自选统计表达或复杂公式无法自动提取，应保留可读数值供复核，评测提取故障不等于业务错误。

逐类给出事件、发送、执行及入账证据，说明首发超时、重试与幂等的关系。提出修复优先级和重放前的核对条件。
