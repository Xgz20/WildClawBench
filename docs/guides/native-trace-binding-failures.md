# 原生轨迹绑定异常与并发收口

## ACode 内建工具映射

ACode 的 `list_mcp_resources`、`list_mcp_resource_templates` 和
`astron_browser_*` 可以直接以工具名出现在原始调用中，对应 MCP 结束事件的
server 是 `acode`。Python 执行器和 General 收集、评分、报告 Skill 的独立
JavaScript 校验器使用相同映射；仍要求工具名完全相同、server 正确、调用参数一致。
不为任意同名工具或其他 server 放宽校验。

2026-11-26，远程 Web 批次 3 的第 26 题在该映射缺失时被拒绝。
原始轨迹调用和结束事件的参数一致，底层诊断为
`NATIVE_MCP_INVOCATION_MISMATCH`。固定执行器 `a0e266c7` 的解析器可离线复现；
补齐映射后同一轨迹可解析为 661 条事件，无缺失项。
原始输入、产物和轨迹保持不变，不据此判断网站质量或补造评分。

## 诊断信息

绑定失败时继续保留每个文件的 `*.binding-error.json`，另写
`staging/metadata/native-binding-<阶段>.json`，列出变化文件数、匹配数和失败原因。
公开错误保留 `TASK_NATIVE_BINDING_AMBIGUOUS` 前缀，并附具体原因，区分未找到
变化轨迹、解析校验失败和多份轨迹匹配。不会公开工具参数或原始工具输出。

## 并发槽和人工处理

以前，控制器已报告完成后发生绑定异常，会直接进入 `NEEDS_ATTENTION`，
既占执行并发，也使调度器停止派发新的待处理题目。

对控制器明确完成后的确定性绑定校验错误，现在先走既有失败取证流程：
停止当前用例的原生进程并核验安静窗口，收集原始轨迹和工作区，校验并封存备份。
成功后本轮记为取证失败（`FAILED`），保留原生 `report_status=completed` 和
`failure_stage=native_trace_validation`，不发布可评分的 execution-ready 回执。
按批次配置保留的排查沙箱继续计入物理占用，但不占执行并发，其余题继续调度。
保留关闭时则按原机制确认回收；回收不明仍计占用。

进程停止或取证封存不成功、远端任务状态不明等情况继续使用
`NEEDS_ATTENTION` 并保留占用，不能仅修改状态来释放并发。

## 用例和轮次重跑

重跑沿用原批次的冻结输入、单元和轮次，采用当前发布且能力兼容的执行器，
为所选轮次创建新 attempt；原版本保留为历史，不回退采用旧版本的成绩。
仅已收口的完成、失败、取消轮次可重跑。整批未收口、远端资源未确认或存在
冲突评分/导出等操作时，重跑仍会被拒绝。单纯排查现场保留不阻止重跑。

`NEEDS_ATTENTION` 需要先恢复原观察/取证并收口，不能直接强行重跑。
对已有终稿的取证故障，应优先评估复用原结果，避免再次执行模型。
新代码不会自动改写旧批次绑定的执行器；部署、旧批次恢复和重跑是独立操作。
