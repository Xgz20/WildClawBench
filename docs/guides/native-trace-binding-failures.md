# 原生轨迹绑定异常与并发收口

## ACode 内建工具映射

ACode 的 `list_mcp_resources`、`list_mcp_resource_templates` 和
`astron_browser_*` 可以直接以工具名出现在原始调用中，对应 MCP 结束事件的
server 是 `acode`。Python 执行器和 General 收集、评分、报告 Skill 的独立
JavaScript 校验器使用相同映射；仍要求工具名完全相同、server 正确、调用参数一致。
不为任意同名工具或其他 server 放宽校验。

2026-11-26，远程 Web 批次 3 的第 26 题在该映射缺失时被拒绝。
原始轨迹调用和结束事件的参数一致，底层诊断为
`NATIVE_MCP_INVOCATION_MISMATCH`。固定执行器 `a0e266c7` 的解析器可离线复现；
补齐映射后同一轨迹可解析为 661 条事件，无缺失项。
原始输入、产物和轨迹保持不变，不据此判断网站质量或补造评分。

## 诊断信息

绑定失败时继续保留每个文件的 `*.binding-error.json`，另写
`staging/metadata/native-binding-<阶段>.json`，列出变化文件数、匹配数和失败原因。
公开错误保留 `TASK_NATIVE_BINDING_AMBIGUOUS` 前缀，并附具体原因，区分未找到
变化轨迹、解析校验失败和多份轨迹匹配。不会公开工具参数或原始工具输出。

## 并发槽和人工处理

以前，控制器已报告完成后发生绑定异常，会直接进入 `NEEDS_ATTENTION`，
既占执行并发，也使调度器停止派发新的待处理题目。

对控制器明确完成后的确定性绑定校验错误，现在先走既有失败取证流程：
停止当前用例的原生进程并核验安静窗口，收集原始轨迹和工作区，校验并封存备份。
成功后本轮记为取证失败（`FAILED`），保留原生 `report_status=completed` 和
`failure_stage=native_trace_validation`，不发布可评分的 execution-ready 回执。
按批次配置保留的排查沙箱继续计入物理占用，但不占执行并发，其余题继续调度。
保留关闭时则按原机制确认回收；回收不明仍计占用。

进程停止或取证封存不成功、远端任务状态不明等情况使用 `NEEDS_ATTENTION`。
它是自动流程的终态：没有活动自动执行 worker，不占执行并发，也不停止其他题派发。
`resource_held` 继续反映尚待核验的沙箱资源，另以 `attention_resources_held` 统计，
不将其误写为已销毁或已确认原生任务停止。此状态不发布可评分回执。
在途题继续运行时，整批仍显示执行中；其余自动流程结束后，整批显示待处理。

每个配置单元及整批的自动 worker 并发分别受限。明确的 AgentCube 鉴权拒绝、
账号配额未生效或运行配置漂移会停止新的派发，保留在途任务；批次预检失败也会阻断启动。
普通单题异常不会被当作这些批次级故障。

## 用例和轮次重跑

重跑沿用原批次的冻结输入、单元和轮次，采用当前发布且能力兼容的执行器，
为所选轮次创建新 attempt；原版本保留为历史，不回退采用旧版本的成绩。
已完成、失败、取消，以及原资源已核验的待人工处理轮次可重跑。
整批自动流程未结束、所选轮次仍有未确认远端资源，或存在冲突评分/导出等操作时，
重跑会被拒绝。未选择的待处理轮次和单纯排查现场保留不阻止其他用例重跑。

对已有终稿的取证故障，应优先复用原结果。未确认原任务状态时不能直接强行重跑。

## 在原批次升级恢复

发布包含 `case-attention-isolation-v1`、`execution-recovery-upgrade-v1` 的框架和对应平台后，
在原批次详情点击「使用修复版恢复」。仅在原观察器退出且批次执行锁空闲时允许预检，
不为升级主动暂停任何任务。Docker 容器更换导致的观察器 hostname 变化，通过实际文件锁
和租约核验处理，不依赖失效的旧 PID 推断安全。

预检展示原/新执行器版本、保留成功轮次数、未派发轮次数、待核验轮次数，以及尚未启动的
自动评分记录数。确认「保留原结果并继续」后，平台登记 `execution_recovery` 操作，
保留原 `engine_json`、批次清单、冻结题目、模型、模板和成功结果。

新执行器通过 `recovery-check` 和 `resume --recovery-receipt` 再次验证清单及 attempt、
session、原 job 与运行配置摘要。已完成轮次跳过；已派发轮次沿用原 attempt 和 job，
只升级取证逻辑；未派发轮次使用新执行器。已有运行配置用于约束同单元未派发轮次，
不会偷偷采用新默认配置。重复提交及观察器重启复用原恢复回执，不创建新的执行版本。

尚未启动且无运行材料的自动评分同步升级读取器，保留评分模型、profile、原连接和能力
配置；已启动评分禁止自动切换。恢复期间不启动等待评分，恢复自动流程结束后再按有效
执行回执评分。原生状态未确认或材料不足的轮次保持待处理，不补零、不自动重复做题。

平台操作历史及框架 `EXECUTION_RECOVERY_REGISTERED` 事件均保留升级记录。
新代码部署本身不会自动升级或恢复任何旧批次，必须显式预检确认。
