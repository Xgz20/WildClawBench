# 通用场景端到端自动化评测指导手册

本文面向评测管理员和执行人员，说明如何通过 Prompt 调用 General E2E Skill，完成通用任务的准备、执行、证据采集、评分、回传和报告。用户通常不需要进入 Skill 目录运行脚本；控制 Harness 按各阶段 Skill 检查依赖、调用入口并保存恢复状态。

本文按 macOS 本地、有人值守的使用方式说明，涉及 AstronStudio、WorkBuddy、QwenWork 和 DoubaoWork。使用前由管理员确认发行包对应的客户端、平台和运行范围；Windows 或其他架构应使用经过该平台验证的发行与操作说明。具体兼容范围见[Harness 集成契约](../../design/e2e/端到端自动化评测Harness接入契约.md#integration-progress)。

首个数据集为 `general-custom60-v1`，包含 60 道自建通用任务，覆盖生产力工作流、代码智能、社交互动、搜索检索、创意综合、安全对齐六类。题目可以交付文件，也可以只回复文字；评分既检查结果，也按任务要求检查执行轨迹。用例范围以冻结的数据集和批次清单为准。

## 术语定义

| 术语 | 定义 |
| --- | --- |
| 控制 Harness | 接收用户 Prompt、调用 General E2E Skill 并组织各阶段工作的 Harness。默认语义评分流程使用 Codex Desktop 的项目与任务能力。 |
| 被评测 Harness | 实际完成题目的桌面 Agent 客户端，例如 AstronStudio、WorkBuddy、QwenWork、DoubaoWork。 |
| 评分 Harness / 语义裁判 | 默认由 Codex Desktop 中的独立单题评分会话担任；也可明确选择 API Judge。自动规则由本地受管 Python Worker 执行。 |
| 管理员 | 选择数据集、任务范围、被评测单元与裁判配置，准备分发包、收集回传并生成报告的人员。 |
| 执行人员 | 接收评测包，在本机运行一个单元的执行、采集、评分和回传，或按阶段与评分人员交接。 |
| 批次 / 单元 | 批次固定数据集、用例范围、发行和裁判配置；单元 `unit_id` 表示其中一个 Harness、被测模型及平台配置组合。同一 Harness 的不同模型使用不同单元。 |
| dataset bundle / suite | 前者是管理员持有的版本化数据集包，包含公开与私有材料；后者是 General E2E Skill 套件，包含 7 个独立 Skill ZIP、发行清单和 Schema。 |
| 题目包 | 以 `__execution.zip` 结尾，包含公开 Prompt、初始 Workspace 和执行契约，不包含 GT、Rubric 或 grader。 |
| 评分包 | 以 `__scoring.zip` 结尾，包含冻结的私有题目定义、评分契约和参考材料；只在执行结束、证据冻结后由评分端消费。 |
| 候选 / 轨迹 | 候选是被评测 Harness 的终态 Workspace；轨迹包含原始会话记录和标准化 transcript，保存回复、工具调用、参数、结果及顺序。纯回复题的答案从绑定会话归档。 |
| attempt | 一次独立执行或评分尝试的身份。恢复沿用原 attempt；重评分创建新评分 attempt，并保留旧证据。 |
| 执行回执 / 回传包 | `collect-evidence-receipt.json` 表示正式采集结果；回传包包含冻结执行证据、submission 和对应评分 attempt，并附独立 SHA-256 回执。 |

## General E2E Skill

| Skill | 使用者 | 功能 |
| --- | --- | --- |
| `prepare-general-e2e-workspaces` | 管理员 | 从 dataset bundle、suite 和配置生成批次、各单元题目包/评分包、报告配置与 Skill 清单。可脱离仓库运行。 |
| `run-general-e2e` | 管理员或执行人员 | 推荐的总入口。按 Prompt 明确选择的阶段组合执行，维护批次/单元状态、打包、导入和恢复。 |
| `execute-general-e2e` | 执行人员 | 操作被评测 Harness 做题，保存一次发送、原生会话绑定和终态。 |
| `collect-general-e2e` | 执行人员 | 归档原始/标准轨迹及资源指标，清理本题进程、冻结候选并生成正式执行回执。 |
| `orchestrate-general-e2e` | 评分控制人员 | 创建独立单题评分目录，调度 Codex 评分会话或 API Judge，校验评分结果并生成 submission。 |
| `score-general-e2e` | 单题评分会话或评分控制人员 | 运行原自动规则、按冻结 Rubric 完成语义判定和合分，输出有中文理由及证据的 `score.json`。 |
| `report-general-e2e` | 管理员 | 校验选定回传，汇总 JSON、领导版 Markdown、审计 Markdown、Excel 和预览。 |

七个 Skill 都可以独立分发，ZIP 名为 `<skill-name>-skill-v<version>.zip`，各自包含声明的共享组件。执行机器和评分机器无需下载 WildClawBench 源码，也不需要另装公共 Skill。独立分发不等于没有运行时依赖：Python、Node、规则运行时和 Excel 渲染依赖仍需由控制 Harness 按 Skill 检查、准备。

General 的安装清单是 **`release-catalog.json`**，批次和单元的 `manifest.json.required_skills` 声明各自依赖。安装时核对名称、版本、`content_sha256` 和 ZIP 的 `zip_sha256`；完全一致的已安装内容可以跨批次复用。同版本内容不同应停止并核对发行来源，不能只凭版本号覆盖。不要将 Web 的 `skills-manifest.json` 或 Web 校验脚本套用于 General。

## 使用方法

### 做题+打分场景

适用场景：管理员已准备好某个单元的评测包，执行人员在本机完成做题、正式采集、评分和回传。

#### 1. 准备被评测 Harness

1. 登录客户端，选择本轮被测模型及推理设置，并与题目包声明核对。
2. 选择本机项目/本地电脑模式；DoubaoWork 须使用“本地电脑”。
3. 设置管理员指定的权限，并让控制 Harness 记录实际显示值。General 不统一要求或自动提升为 `full-access`；例如 WorkBuddy 可冻结 `default-sandbox` 或 `full-access`，DoubaoWork 使用实际权限标签。
4. 保持桌面解锁，确保执行进程与当前登录的控制台用户一致，并检查没有冲突的活动任务或需要保留的草稿。
5. 为评测准备独立、较短的工作目录，给 Workspace、原始轨迹和回传包预留磁盘空间。

模型、推理和权限以批次配置及发送前回读为准。包内明确指定模型时，实际值必须匹配；配置明确为保持当前模型时，执行前记录实际可见值。`keep-current` 不能替代实际模型记录，客户端的“标准”“高级”“自动”等档位也不能冒充已确认的底层模型 ID。评测期间不要人工切换配置。

#### QwenWork Token 采集开关（由控制 Harness 按 Skill 管理）

新批次需要 Token 指标时，在 Prompt 中明确要求准备进程级 Token 暴露。控制 Harness 使用 General execute 随包提供的专用启动入口，仅向新 QwenWork 子进程注入 `QODERCN_EXPOSE_TOKEN_USAGE=1`，随后重新 probe，并为新队列启用 `--require-token-exposure`。

该变量不能写入题目 Prompt、系统全局环境或评分 Agent 配置；对已启动客户端仅设置终端变量不会生效。安全启动前必须确认原生会话空闲并核对应用、进程和端口身份。已有队列沿原冻结配置恢复，不在运行中补开开关或重启客户端。

开关生效后，采集器仍须逐请求对账原生用量。旧 masked/缺失记录不能回填；无法可靠观测的字段保持未知。

#### 2. 准备桌面客户端调试模式和依赖

在正式执行前，让控制 Harness 按所装 General Skill 运行只读 probe，检查客户端安装、真实主进程、调试端点、当前模型/权限、状态库和轨迹来源。probe 本身不启动或重启客户端、不发送 Prompt。

常用 loopback 端口如下；实际端口以本轮冻结配置和监听进程核验结果为准：

| 客户端 | CDP 地址 |
| --- | --- |
| Codex Desktop | `http://127.0.0.1:9230` |
| AstronStudio | `http://127.0.0.1:9240` |
| WorkBuddy | `http://127.0.0.1:9229` |
| QwenWork | `http://127.0.0.1:9250` |
| DoubaoWork | `http://127.0.0.1:9260` |

应用支持动态发现或显式指定安装路径；自定义安装、多个安装副本或识别歧义时，在 Prompt 中补充实际 `.app` 路径和需要使用的端口。仅端口可连接还不够，必须确认它属于目标安装的主进程。

需要开启调试模式时，由控制 Harness 按该客户端入口处理，并在重启后重新 probe。General 随包的 `restart_macos_desktop_debug.sh` 是 Codex 的托管重启入口；被测客户端使用各自的安全启动方式，不能拿该脚本通用于所有客户端。有活动任务或发送状态不明时，先保留现场并恢复原任务。

执行和评分不依赖 Docker。控制 Harness 应准备与发行匹配的 Node/锁定 Driver 依赖；自动规则使用 Python 3.11、`uv` 创建的专用虚拟环境和锁定依赖，必要的 Chromium 安装在该运行时内。Excel 报告另需带 `@oai/artifact-tool` 的 Node runtime。上述自动化依赖安装在控制目录、Skill Driver 或专用运行时中；被评测 Harness 自己按题目安装的业务依赖属于候选行为。

#### 3. 安装 Skill

可以手动解压安装，也可以在 Codex 控制任务中通过 Prompt 安装。常用做法是安装同一 suite 的全部 7 个 Skill；仅在执行/评分机器工作时可省略 prepare，安装清单仍须覆盖本次所选阶段。

手动安装时，先按发行清单核对 ZIP，再将各 Skill 顶层目录放入 Codex 用户级 Skill 根目录。macOS 常用 `$HOME/.agents/skills`，Windows 常用 `%USERPROFILE%\.agents\skills`；安装位置可用不代表该平台已具备客户端执行能力。不要装入题目 Workspace，也不要将私有评分材料或评分 Skill 加入被评测 Harness 的可见任务材料。

自动安装 Prompt：

```text
请安装下面这套 General E2E Skill，并输出安装核验结果。

Suite ZIP：/absolute/path/general-e2e-suite-<release_id>.zip
发行文件清单：/absolute/path/general-e2e-release-manifest.json
本批次清单：/absolute/path/<batch_id>/manifest.json

安装要求：
1. 校验 suite 与发行清单的 SHA-256，读取 suite 内 release-catalog.json，以其 skills 为安装清单；安装 prepare Skill 后使用其 verify-release 入口再次核验 suite。
2. 安装 prepare-general-e2e-workspaces、execute-general-e2e、collect-general-e2e、orchestrate-general-e2e、score-general-e2e、report-general-e2e、run-general-e2e。
3. 逐个核对 zip_sha256、唯一顶层目录、skill-metadata.json 的 name/version，以及按发行声明算法计算的 content_sha256 和共享组件摘要；拒绝越界路径、重复成员及 Skill 内符号链接。
4. 安装到当前用户的 Codex Skill 目录。已有名称、版本和内容摘要一致时复用。同版本内容冲突时停止并报告；版本不同时，若旧路径仍被未完成批次引用，保留原目录并在独立发行目录安装新版；否则先把旧版备份到 Skill 根目录之外，再校验并安装。
5. 安装后与本批次 required_skills 逐项核对，列出实际路径、版本、内容摘要及 installed/skipped/failed 状态。保留运行中的旧批次所依赖的冻结 Skill 路径。
6. 此次仅安装；若 Codex 尚未发现新 Skill，提示重新打开控制任务后使用。
```

若管理员只提供批次分发目录而没有 suite，可将前三行替换为 `发行清单：.../release-catalog.json`、`Skill ZIP 目录：.../packages` 和 `本批次清单：.../manifest.json`；对应执行逐个 Skill ZIP 与清单核验，不运行依赖 suite 的 `verify-release`。按清单中 ZIP 文件名在该目录定位；suite 使用 `skills/`，批次目录使用 `packages/`。

工作区源码里的同名 Skill 不能替代已经冻结的发行。管理员也可以将经校验的发行解压到固定目录，再按 Codex 支持的方式建立发现入口；评分任务仍须使用编排状态中冻结的绝对 Skill 路径。

#### 4. 输入一个 Prompt

General 的做题和评分需要题目 ZIP、评分 ZIP、同批次 `report-config.json`，以及一个独立工作根目录。评分配置包含裁判协议、模型和推理强度，不能省略后任由控制会话默认值替代。

在 Codex Desktop 新建控制任务，输入：

```text
请使用 $run-general-e2e 完成以下 General E2E 单元的执行、collect-evidence、评分和打包回传。

题目包：/absolute/path/<batch_id>__<unit_id>__execution.zip
评分包：/absolute/path/<batch_id>__<unit_id>__scoring.zip
报告及裁判配置：/absolute/path/<batch_id>/report-config.json
工作根目录：/absolute/path/GeneralE2E/worker-<batch_id>-<unit_id>

按已安装且与包清单一致的 General Skill 操作，核对批次、unit、dataset digest 和任务范围。
只解压题目包到独立 execution unit；评分包只交给执行结束后的私有评分流程。
按包中请求配置回读被测模型与推理设置，权限使用我已经在客户端设置的模式并冻结实际值。
执行使用该 Harness 的默认槽位，UI 操作保持单路；语义评分并发为 3。
语义裁判严格使用 report-config.json 的 judge 配置，每题创建独立评分任务；automated 只运行规则，hybrid 运行规则加语义评分。
归档原始轨迹、标准 transcript、资源覆盖和中文逐检查点评分证据。
保持每题一次发送；中断时恢复原 attempt。未知交互或身份不明确时保存状态并说明原因。
最终返回 collect receipt、submission、return ZIP 和外部 package receipt 的绝对路径。
```

控制 Harness 将核验输入、准备运行环境、执行用例、采集并冻结证据，然后按任务类型评分、校验 `score.json`、生成 `submission.json` 和回传包。流程完成不代表每题满分；执行异常、未评分和评测异常会保留在结果中。

针对具体客户端，可在上述 Prompt 后追加：

| Harness | 追加要求示例 |
| --- | --- |
| AstronStudio | “按题目包回读当前模型/推理/权限，执行并发 3；每题绑定原生 thread、turn、session 和完整 Workspace。” |
| WorkBuddy | “预期模型 xopglm52，预期权限 default-sandbox，发送前回读；执行并发 3。按原生 session JSONL 采集用量。”示例值须改成管理员要求。 |
| QwenWork | “本包为 keep-current，回读当前模型档位及权限并冻结；执行并发 3。新队列发送前准备进程级 Token 暴露并验证，项目预建后按 manifest 顺序发送。” |
| DoubaoWork | “使用本地电脑，回读与包匹配的模型显示值和当前权限；执行并发 1，保持有人值守。未知授权、追问或未结束的后台工具交付时暂停。” |

首次换机、升级客户端/Skill 或切换模型后，建议先准备独立的 1–3 题小批，以执行并发 1 运行。批次任务范围一旦冻结，不通过删除清单条目来缩小范围。

QwenWork 若要自动跳过可识别的追问，必须在本轮策略中明确写出：“允许对已绑定会话中唯一的追问卡片点击‘跳过’，不代答；其他授权或弹窗保留现场。”控制 Harness 才可启用对应策略，操作记录进入 journal。该授权不适用于未知系统弹窗或文件授权。

#### 5. 获取回传包

成功打包后，控制 Harness 返回以下两个文件：

```text
<batch_id>__<unit_id>__return__<package_id前16位>.zip
<batch_id>__<unit_id>__return__<package_id前16位>__package-receipt.json
```

将两者一起交给管理员。ZIP 已包含该单元的正式证据、`scoring/submission.json` 和所引用的评分 attempt；单独发送 Excel、score.json 或候选目录不足以复核。评分 runtime 副本不进入回传。

保留工作根、原始执行目录、冻结 Skill 和私有评分根，直至管理员确认导入成功。恢复校验可能同时核对原始 Workspace 与冻结候选，不要在回传后立即清理工作目录。

#### 6. 中断后恢复

重新打开原控制任务，或新建控制任务并提供原工作根和输入路径：

```text
请使用 $run-general-e2e 恢复这个 General E2E 单元，完成原来已选择但尚未结束的阶段。

工作根目录：/absolute/path/GeneralE2E/worker-<batch_id>-<unit_id>
题目包：/absolute/path/<batch_id>__<unit_id>__execution.zip
评分包：/absolute/path/<batch_id>__<unit_id>__scoring.zip
报告及裁判配置：/absolute/path/<batch_id>/report-config.json

先读取磁盘状态、原执行队列和评分 orchestration，沿用原冻结 Skill、配置、attempt 与评分 thread。
不确定是否发送的题目只核对原生记录，不重发。已有评分任务继续等待或检查同一 thread。
列出恢复结果、当前仍运行的任务和需要人工处理的原因。
```

`NEEDS_ATTENTION` 或 `NEEDS_HUMAN` 必须按具体原因处理。不要删除锁、修改回执、替换冻结 Skill 或重新执行一次发送。需要重评分时，使用独立重评分入口保存新 attempt 和来源关系。

### 全流程场景

适用场景：同一台机器承担管理员、执行和评分角色，从冻结数据集及 Skill 套件开始完成全部阶段。

#### 1. 一次性准备

1. 取得管理员提供的 dataset bundle、General suite 和发行清单，按前述方式安装 7 个 Skill。
2. 设置被评测客户端，准备 Codex Desktop 的独立评分任务能力和本地规则/报告运行时。
3. 选择独立控制目录，分别存放批次、执行 unit、私有评分和回传。dataset bundle 含私有评分材料，不交给被评测 Harness。

General prepare 可以直接消费 dataset bundle 和 suite，不要求先下载仓库。需要从仓库任务制作新数据集或新 Skill 发行时，由管理员先完成冻结和验包，再使用以下流程。

#### 2. 输入全流程 Prompt

下面以 AstronStudio 三题覆盖三类评分方式为例；模型、平台和版本改为本轮实际值。示例裁判为 `gpt-6-sol/high`，实际应由管理员选择账户可用模型，并在准备时固定。

```text
请使用 $run-general-e2e 完成一次通用端到端评测的准备、执行、collect-evidence、评分、打包回传、import-return 和报告。

数据集：/absolute/path/general-custom60-v1.dataset.zip
Skill 套件：/absolute/path/general-e2e-suite-<release_id>.zip
批次输出目录：/absolute/path/GeneralE2E/batches
执行及评分工作根：/absolute/path/GeneralE2E/work

用例：
- 01_Productivity_Flow_task_005_support_handoff
```

### 多电脑场景

管理员准备批次，执行人员处理各自单元，再离线交回 ZIP 和回执。无需固定 `admin/worker` 参数，Prompt 明确阶段与输入即可。

管理员分发和留存的文件：

| 文件 | 用途 |
| --- | --- |
| 对应单元 `__execution.zip` 与 `__scoring.zip` | 执行人员所需输入；两个包必须保持隔离。 |

同一逻辑 unit 不拆到多台机器并发执行。需要分片时，管理员在准备阶段定义不同单元和任务范围；跨单元比较须披露范围差异。

## 各个 Skill 用法详解

### 管理员准备能力：`prepare-general-e2e-workspaces`

从 dataset bundle、suite 和 prepare 配置生成独立批次。无需仓库 checkout，也不启动客户端。

```text
请使用 $prepare-general-e2e-workspaces 准备 General E2E 批次。

数据集：/absolute/path/general-custom60-v1.dataset.zip
Skill 套件：/absolute/path/general-e2e-suite-<release_id>.zip
准备配置：/absolute/path/prepare-config.json
输出目录：/absolute/path/GeneralE2E/batches

先验证 dataset/suite 与配置，按 manifest 顺序生成包，完成后执行 verify-batch。
返回批次 manifest、report-config、release-catalog、各单元 execution/scoring ZIP 及 Skill ZIP 清单。
```

每个单元有一对 `__execution.zip` / `__scoring.zip`；批次根有 `manifest.json`、`report-config.json`、`release-catalog.json`。初始素材、任务所需 Skills/Env/Warmup 等声明按冻结数据集处理，不擅自删改题意、参考答案、Rubric 或评分权重。新准备协议将原 `/tmp_workspace` 映射为当前目录 `.`，因为客户端cwd已是每题Workspace；同时保存映射与Prompt摘要。旧包不改写，评分保留其冻结路径映射兼容。

运行时修复、资源补采、逐题结果选择与研发数据打包，参见[证据修复与有效结果交付](证据修复与有效结果交付.md)。

### 1. `run-general-e2e`

组合用户选择的阶段并维护恢复状态。稳定顺序为 `prepare → execute → collect-evidence → score → package → import-return → report`；其中 score 由编排与单题评分 Skill 协作完成。

```text
请使用 $run-general-e2e 检查 /absolute/path/extracted-unit 的已有状态，恢复原先选择的 execute、collect-evidence、score、package 阶段。
使用已冻结的输入、Skill 路径、队列和评分任务；返回下一步动作以及任何身份或哈希冲突。
```

batch 根管理准备、导入、报告；unit 根管理执行、采集、评分、回传。状态在各自 `.general-e2e/` 下持久化。“采集证据”与“导入回传”是不同阶段，不能只写一个含义不明的 collect。

### 2. `execute-general-e2e`

执行 execution unit 中的题目，记录一次发送和原生终态；正式候选冻结交给 collect Skill。

```text
请使用 $execute-general-e2e 执行 /absolute/path/extracted-unit 中 manifest 声明的全部任务。

先运行对应 Harness 的只读 probe，核对原生会话空闲、模型、权限和完整 Workspace。
执行并发设为 1，UI 单路。按原 Prompt 执行，逐题保存发送与 session/turn/cwd 绑定及终态。
不确定发送或未知交互时保留原 attempt。完成后返回执行队列、各题状态和交给 collect 所需的路径。
```

执行方式、队列槽位及允许的交互策略在开始前冻结。需要人工接管时可保留 `NEEDS_HUMAN`；人工操作必须记录，能否继续形成正式结果取决于该客户端的证据与回执支持，不能手改 `execution_mode` 掩盖介入。

### 3. `collect-general-e2e`

这是 General 进入评分前的正式证据门禁：按原生身份归档 rollout/transcript，逐字段采集资源，清理本题进程，等待 Workspace 静默并冻结候选。

```text
请使用 $collect-general-e2e 收口 /absolute/path/extracted-unit 中已取得可信终态的任务。

读取原执行状态，逐题核对原生身份、Prompt、终态、原始轨迹和资源来源。
执行真实平台进程清理与候选冻结，保存原始/标准轨迹、指标、证据清单和正式 execution-record。
完成后运行 verify-only，核对冻结候选与原始 Workspace，生成并校验 receipts/collect-evidence-receipt.json。
缺失字段保留 null、已知小计和覆盖率；返回未完成或需人工处理的任务列表。
```

正式证据位于 `evidence/tasks/<task_id>/<execution_attempt_id>/`。常用入口为该目录的 `execution-record.json`、`resource-metrics.json`、`evidence-manifest.json` 和 `trace/trace-index.json`；原始文件名随客户端不同，通过 trace-index 定位，不按“最近日志”猜测。

合法的资源 `partial` 不必然阻断评分，例如缺少 Cache Write；必需的身份、候选或评分所需轨迹缺失会阻断相应任务。仅依赖文件的部分 automated 规则可按 score Skill 的严格准入处理 partial 工具轨迹；控制人员不能自行放宽条件。

### 4. `orchestrate-general-e2e`

从正式执行证据和 scoring ZIP 为每题创建私有评分 attempt，按固定裁判和槽位调度，校验结果后生成完整 submission。

```text
请使用 $orchestrate-general-e2e 完成这个 General E2E 单元的评分编排。

执行 unit：/absolute/path/extracted-unit
评分包：/absolute/path/<batch_id>__<unit_id>__scoring.zip
报告及裁判配置：/absolute/path/<batch_id>/report-config.json
冻结 score Skill：/absolute/path/installed/score-general-e2e
私有评分输出根：/absolute/path/private-orchestrations
编排 ID：general-score-01
语义评分并发：3

使用报告配置指定的裁判协议、模型和推理强度。每题独立 attempt；automated 只运行规则，hybrid 先规则后语义。
Codex 后端按推荐动作创建独立项目/评分任务，保存 thread 和 wait cursor。
每题必须通过 verify-score 才登记结果；所有任务终态后生成完整 submission.json，保留 valid、evaluation_error 和 unscored。
```

控制会话负责调度，不在自己的上下文里替所有题目判分。评分任务由 Codex Desktop 项目/任务接口创建，模型和推理强度使用动作中的冻结值。任务显示完成后仍须验证 `score.json`；有效零分、合法评测异常与未评分分别保存。

#### 可选：使用 API Judge

准备阶段将 `judge.protocol` 设为 `api-judge-v1`，填写具体模型和推理配置；评分阶段再提供私有 API runtime JSON。支持的 transport 为：

| provider | 接口路径 |
| --- | --- |
| `openai-chat-completions` | 在 base URL 后追加 `/chat/completions` |
| `openai-responses` | 在 base URL 后追加 `/responses` |
| `anthropic-messages` | 在 base URL 后追加 `/v1/messages` |

```text
请使用 $orchestrate-general-e2e 按 API Judge 配置完成评分。

执行 unit：/absolute/path/extracted-unit
评分包：/absolute/path/<batch_id>__<unit_id>__scoring.zip
报告配置：/absolute/path/<batch_id>/report-config.json（judge.protocol 已冻结为 api-judge-v1）
冻结 score Skill：/absolute/path/installed/score-general-e2e
API runtime 配置：/private/path/api-runtime.json
私有评分输出根：/absolute/path/api-orchestrations
编排 ID：general-api-score-01
语义评分并发：3

凭据只从配置声明的环境变量读取；不写入题目包、Prompt、日志或报告。
校验 provider、端点、模型、证据/输出预算与重试配置；完成后 verify-score 并生成 submission。
```

API runtime 按 score Skill 随包说明创建，包含 `provider`、`base_url`、`credential_env`、预算、请求超时和重试策略。API Judge 受冻结的证据预算限制，会记录截断与省略，不能引用未实际提供的证据；它没有 Codex 评分会话的按需分页回查流程。失败时保存审计与评测异常，不自动换模型或切到 Codex。

### 5. `score-general-e2e`

按单题冻结契约完成评分。正常使用由 orchestrate 自动准备目录和 Prompt，无需用户逐题手工操作。

| 题目类型 | 评分方式 |
| --- | --- |
| `automated` | 仅运行原自动规则，语义组件为 `not_required`。 |
| `hybrid` | 自动规则 + 指定语义裁判，按任务原权重合分。 |
| `llm_judge` | 由指定语义裁判按 Rubric 判定。 |

人工复核时，优先让 orchestrate 从冻结候选创建新的评分 attempt，并生成匹配的评分 Prompt。单题评分会话读取 Prompt 中给出的 score Skill 绝对路径、版本和入口摘要，不能自行从同名 Skill 中挑选。

评分先验证候选和私有材料；需要规则时在一次性 runtime 副本中执行；语义判定通过证据目录和分页查询读取文件/轨迹。每个 Rubric 检查点都写中文理由，说明为何是满分、零分或部分分，附可定位证据及反例检查。声称“全程未发生某行为”时须无过滤覆盖完整相关 transcript，关键词无命中不足以证明。

最终输出 `score.json`、组件结果和评分审计，执行 `verify-score` 复核。候选本身内容错误按 Rubric 得分；证据不足、依赖错误或裁判失败保留评测异常/未判定。已有终态评分不覆盖，重评分使用新 attempt。

### 6. `report-general-e2e`

从管理员批次中已导入、唯一选定的回传包生成报告。原始 return ZIP 先由 run Skill 导入，report 不自行选择最新包或补评分。

```text

先 validate-inputs，核对每个 unit 的选定 package、receipt、submission、score 和资源摘要。

核对分母、分数、资源覆盖和关键范围，扫描公式错误，并逐张检查预览。
保留全部冻结任务的状态，未知量不补零；返回 report receipt 和各文件绝对路径。
```

输出目录须位于 batch root 内且不存在或为空。完成后有：

- `general_e2e_report_data.json`：可复算报告数据和完整长字段。
- `通用场景端到端自动化评测报告.md`：领导版汇总。
- `通用场景端到端评测审计.md`：状态、裁判、资源覆盖和来源审计。
- `通用场景端到端自动化评测报告.xlsx`。
- `previews/excel-validation.json`、各 Sheet 的 PNG 预览及 `receipts/report-receipt.json`。

Excel 为 **9 张公共表 + 每单元 1 张评分详情表**：总览、效率对比、分类对比、难度对比、Agent 能力对比、模态对比、工具调用对比、用例对比明细、各单元评分详情、资源覆盖与异常。一个单元为 10 Sheet，四个单元为 13 Sheet。评分详情包含检查点、判词与轨迹引用；长文本在 Excel 中节选，全文保留于 JSON。

展示分数为 0–100，底层 score 和 CLI 兼容数据仍为 0–1。有效均分仅包含 `valid` 任务，真实 0 分纳入，`evaluation_error` 和 `unscored` 不补零。每项资源分别展示总量、已知小计及覆盖率；覆盖不完整时完整总量为空。

资源统计对应被测任务，不把控制器和裁判消耗混入被测 Token。任务耗时、执行流程耗时及批次壁钟分别统计；模型请求数依客户端原生来源注明口径，不能当作完整 HTTP 重试次数。详细计算见[通用指标说明](../../design/general-e2e/通用场景端到端自动化评测指标说明.md)。

## 模型、权限和并发规则

- 被测模型与语义裁判分别配置；控制会话自身模型不自动成为裁判。裁判协议、模型、推理强度由 `report-config.json` 冻结。
- 执行前由用户设置被测模型、推理和权限；Driver 核对请求值与实际值。保持当前模式也必须记录实际观察，底层模型无法确认时显示未知。
- 权限按该 Harness 与批次要求冻结；允许修改题目 Workspace 不等于允许控制器代答业务追问或批准未知授权。
- AstronStudio默认1个后台槽，保持逐thread原生流租约门禁；更高值须有目标客户端实证。WorkBuddy/QwenWork默认3槽、可配置1–8；DoubaoWork默认3槽、接受1–3。各端UI派发仍单槽，不能由配置值冒充实测并发。
- 所有客户端 UI 操作保持单路；后台槽位占用与原生请求实际重叠分别留证，不用槽位数推定真实并发。
- Codex/API 语义评分默认 3 槽，上限 8。automated 不占语义槽，hybrid 完成规则后进入语义槽；规则 Worker 不因此变成三路执行。
- 题目 `timeout_seconds` 不限制被测 Harness 总执行时间，也不作为评分条件。当前新建 General 评分编排不设置任务级线程 deadline；CDP/UI、HTTP、规则 Worker 和进程清理仍有各自的基础设施超时。
- 同一批次恢复沿用已冻结配置；更换模型、裁判、队列槽位或发行时按对应入口建立新运行，保留原证据。

## 候选产物保护

执行时只有被评测 Harness 按题意修改 Workspace。执行结束后，由 collect 处理本题残留进程、等待静默、冻结候选并发布正式证据；控制器和评分会话不能代修候选。

General 候选默认完整保留目录树，`.git`、`node_modules`、`__pycache__` 等可能是任务产物，不沿用 Web 的统一过滤规则。确需排除目录时须使用有理由、可审计的候选策略；不能为了让包变小临时删文件。安全相对符号链接按契约校验，不跟随越界链接读取宿主文件。

评分使用只读 `candidate-original/` 和一次性 `runtime/workspace/`，私有 GT 仅在规则运行时后置。规则测试产生的文件留在 runtime 中；runtime 不进入回传。最终回复、原始轨迹、评分证据和哈希关系保持可追溯。

发现身份不符、残留进程、持续写入或候选漂移时，保留现场并处理实际原因。重新做题使用新批次/执行身份；重评分使用独立评分 attempt。不能编辑回执或重算摘要掩盖变化。

`integrity.valid=false` 是完整性门禁失败，不等于能力零分。字段资源缺失与必要评分证据缺失也要区分：前者可带覆盖率报告，后者影响相应任务能否有效评分。

## 常见问题

### 提示自动化依赖安装失败

将具体错误、所用 Skill 版本和运行时路径交给控制 Harness，按随包锁文件检查网络、缓存、Python/Node 和目录权限。规则运行时用专用虚拟环境；不要通过修改候选、换用旧 Web Driver 或放宽依赖版本处理控制环境问题。

### 为什么通用评分会安装 Playwright，是否还需要 Docker

部分自动规则需要浏览器能力，因此完整规则运行时包含锁定的 Playwright/Chromium。General 的执行与评分不依赖 Docker；浏览器运行时与被测任务的业务依赖分别管理。

### 只有题目包和评分包，能否直接评分

还需同批次 `report-config.json`，以及执行后形成的正式 unit 和 collect receipt。评分配置不能靠猜测补齐。管理员应同时提供发行清单与所需 Skill ZIP，执行人员无需取得含全部私有数据的 dataset bundle。

### 已安装同版本 Skill，为什么仍提示不一致

先核对 `release-catalog.json`、`required_skills`、实际安装路径和内容摘要。不同批次可以复用名称、版本及内容一致的 Skill；同版本不同内容属于需要核对的发行差异，不能只改版本字段或忽略哈希。已有评分任务继续使用它冻结的绝对入口。

### 当前模型或权限与包内配置不一致

在发送前停止并按管理员要求设置客户端。已执行的材料不能通过修改 manifest/JSON 换成另一模型；需要改配置时准备新批次。客户端自动路由的底层模型无法确认时，应记录可见档位和 unknown，而不是填写裁判模型。

### AstronStudio 或其他客户端 probe 未就绪

检查登录、锁屏、当前控制台用户、真实安装位置和调试端点。多安装或自定义路径时提供实际 `.app`，让控制 Harness 核对监听 PID、状态库和 UI。probe 不自动代表启动授权或重启结果；按该客户端支持的入口完成准备后再生成新 probe。

### macOS 出现“ChatGPT.app 想要控制 AStudio.app”

这是 Apple Events 自动化授权提示。当前共享发现、进程识别、锁屏探测和 Codex 托管退出使用本机进程/系统查询与有界信号，不依赖该授权。核对实际调用的 Skill 是否为当前冻结发行，以及是否有其他自动化入口；不要将所有系统“允许”按钮设为自动点击。

### Codex Desktop CDP 连接失败

先核对 9230 的实际监听者和目标应用。需要为承载当前控制任务的 Codex 开启调试模式时，先持久化状态，再使用 orchestrate 随包的一次性托管重启入口；恢复后检查重启状态为 `PASSED`，继续原 orchestration。

### Codex Desktop 反复重启且无法停止

历史自动化曾因遗留 launchd 任务重复启动客户端。先停止评测，核对下面三个 WildClawBench 重启任务；确认存在对应遗留任务后可在终端移除，任务不存在时返回非零不表示又发生故障：

```bash
launchctl remove com.wildclawbench.general-e2e.codex-refresh
launchctl remove com.wildclawbench.general-e2e.codex-debug
launchctl bootout gui/$(id -u)/com.wildclawbench.desktop-debug-restart.codex
```

当前入口使用 `KeepAlive=false` 的一次性 LaunchAgent。日志和状态位于 `~/Library/Application Support/WildClawBench/desktop-debug-restart/<run-id>/`；核对该目录后恢复原流程，不自行改用 `launchctl submit`。这些命令只针对上述重启任务，不是通用客户端清理命令。

### 重启时出现退出确认框或“Trust this folder”

当前 Codex 托管重启入口对已核验根进程先 TERM，再按有界等待和身份复核决定 KILL，不通过通用 UI 点击批准退出。若结果未达到 `PASSED`，保留日志处理。

“Trust this folder”应先核对是否为本轮新建的精确项目路径。已授权信任本轮文件夹时，控制 Harness 可按对应入口确认；该授权不延伸到陌生目录、系统权限弹窗或题目中的业务授权。

### 纯回复题没有生成文件，是否执行失败

依据原生业务终态、绑定会话和任务契约判断。纯回复题从轨迹归档最终回复，不要求生成无关文件；只有任务本身要求交付的文件缺失时，才按原 Rubric 评价。

### 原始会话轨迹和得分依据在哪里

执行 unit 的 `evidence/tasks/<task_id>/<attempt_id>/trace/trace-index.json` 指向原始文件、标准 transcript 和身份绑定证据；回传包内位于 `unit/evidence/`。评分 attempt 中有 `score.json`、规则组件和语义审计；Codex 语义评分的 `semantic/query-log.json` 记录分页取证。Excel 单元评分详情给出检查点、中文判词和轨迹引用，完整长文本保存在报告 JSON。

### Token 显示未知、工具为零，是否采集失败

先看字段状态和覆盖率。真实纯回复任务可以有 0 次工具调用；来源缺失则应为 null，不能写成 0。QwenWork 需要启动时的 Token 开关和逐请求对账；DoubaoWork 未暴露可信累计 Token 时保留未知。上下文窗口占用、订阅额度、积分和日志文件大小均不能替代累计 Token。

### 评分任务提示模型容量不足

保留原 thread 和评分 attempt，控制 Harness 按原 cursor 等待或检查。不要立即创建替代评分任务、切换模型或重复发送评分 Prompt。原任务明确失败后保存审计；需要再次评分时使用新的独立重评分流程，不改写原结果。

### 评分任务没有 Browser，是否无法评分

General 默认语义评分依靠冻结候选、文件和轨迹查询，不统一要求 Web 评分使用的桌面 Browser。自动规则若需要浏览器，则由本地受管 Playwright runtime 提供。具体证据需求以该题规则和 Rubric 为准，不能把 Web Browser 门禁直接套在通用纯文本题上。

### 用例耗时超过题目中的 timeout_seconds

General 不据此终止被测任务或扣分。继续等待可信原生终态、明确异常或用户停止要求。低层 UI/CDP、API 请求和规则 Worker 的保护超时分别处理，不转换为能力零分。

### 出现未知授权、追问，或流程进入 NEEDS_ATTENTION / NEEDS_HUMAN

让控制 Harness 返回原 attempt、已发送状态、绑定目录和具体原因。未授权的追问不代答、未知授权不批准；人工处理需保留记录。DoubaoWork 存在原生文件授权历史但没有可核验人工介入回执时，不能按零人工操作的自动结果收口。不要删除状态或锁以跳过校验。

### 收到同一 unit 的两个回传包

相同 archive SHA 可幂等导入；不同内容分别保存并清空当前选择。管理员核对 attempt 和评分来源后明确选择完整 package ID。报告不能自动挑最新目录，也不能只挑高分回传。

### Excel 生成失败或缺少某个单元

先确认所有批次 unit 都已唯一选择回传，再检查报告输出目录和带 `@oai/artifact-tool` 的 Node runtime。依赖不可用时保留已完成的执行、评分和回传，补齐后生成新报告目录；不要重新做题。缺单元应补齐回传，不能删 manifest 条目让报告通过。
