## 已核实的两层问题

AgentCube 路由返回 HTTP 200，正文为
`{"code":20007,"msg":"sandbox unreachable","data":null}`。原 `download()` 只检查 HTTP
状态，把这段错误 JSON 当成 `exit_code` 文件返回，`poll_job()` 随后执行 `int()`，
因此页面显示 `ValueError`，掩盖了实际的沙箱访问故障。

本机 AgentCube 只读参考 checkout 为 `feature_ifly` /
`3cadd8e0dc1531a5cbf035f8239de4086673987f`，工作区干净。其路由代理在连接拒绝或
其它转发故障时返回 20007；公共错误响应函数有意使用 HTTP 200 JSON。此源码解释
错误码和响应形状，不证明服务器 AgentCube 正在运行这个 checkout，也不足定位
到底是 Pod、节点、网络还是来宾系统触发故障。

## 框架修复

- 原始和流式文件下载识别无附件标识的标准网关错误 JSON，20007 / 20008 等保留
  稳定错误码及 `platform_code`，进入 AgentCube 故障域，不再误报整数解析失败。
- JSON 附件仍按原字节下载，流式接收采用有界探测；错误正文不覆盖旧文件，不遗留
  半截下载文件。
- 短暂故障只重试读取同一会话、同一远程作业，不再次创建会话或重发 Prompt。
- `exit_code` 缺失时核对原作业 `pid`；两者都缺失报 `REMOTE_JOB_STATE_MISSING`，
  不把丢失的作业当作持续运行。损坏的退出码报结构化、状态不明错误，不当成成功。
- 保留现有待处理 / 人工恢复策略，未增加自动重做业务任务或删除原会话的行为。
