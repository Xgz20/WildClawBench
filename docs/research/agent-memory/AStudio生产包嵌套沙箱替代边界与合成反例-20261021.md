# AStudio 生产包嵌套沙箱：替代边界与合成反例

2026-10-21，北京时间。工作分支 `feat/memory-e2e`，所有代码修改仅在 `.agents/memory-e2e`。
本轮仅使用安装包 AStudio 3.5.0 的原 arm64 内核 ACode 1.0.5-rc.3；没有修改、重编、注入或改签。
原生沙箱、已有 OS 边界与正式发送门禁均保持；普通实例和登录账号未动，正式20题未启动。

## 新发现：原生权限配置能保护工具，不能独立覆盖后端

生产 CLI 实际暴露 `sandbox --permission-profile NAME --include-managed-config`，
能够从私有 `ACODE_HOME` 读取原生 filesystem/network 配置并由原内核生成、安装策略。
本轮新合成目录分别代表当前单元、非目标客户端、旧用例、旧重复和原生只读/私有区域。
没有对 Codex 或其他客户端的真实记忆目录进行任何访问尝试。

首次独立实验 `astudio-production-native-policy-20261021-r1`：

| 生产内核实测 | 结果与解释 |
|---|---|
| 原生受限命令及其子进程：文件/符号链接/旧单元/只读写入/网络操作 | 58/58，通过 |
| 两代受限进程的实际 OS 读取策略查询 | 10/10，通过 |
| 原生策略外再加一个仅 `(allow default)` 的 Seatbelt | exit71，`sandbox_apply: Operation not permitted` |
| 原生策略外加合成非目标目录拒绝的 Seatbelt | 同样 exit71 |
| 独立生产 app-server，读取当前单元的正向对照 | RPC 返回精确合成事实，OS 允许 |
| 相同 Profile 的 app-server，读取非目标/旧用例/旧重复三个目录 | 3/3 都返回精确合成事实，OS 允许；隔离失败 |
| 非目标、旧单元、原生只读区的合成事实与安装内核 | 前后 SHA 一致 |
| 探针 app-server 退出 | stdio EOF 后正常 exit0；没有 thread/turn/model 请求 |

因此 **仅使用原生 Profile 的方案明确 NOT_ADMITTED_BACKEND_COVERAGE_GAP**。
不能用 58 项工具检查通过掩盖后端的三次越界读取，也不能撤掉现有外层 OS 边界。
最宽的外层 Profile 也产生重入错误，进一步排除了通过给目录增加权限来修复冲突的假设。

原始代码只读核验亦与此吻合：`app-server/src/request_processors/fs_processor.rs` 的文件读取传递
`sandbox=None`；工具策略不自动成为主内核全进程的 OS 策略。
`memories/write/src/phase2.rs` 还会为整理代理设置自己的 WorkspaceWrite、无网络策略。
这些源码线索不能替代生产二进制实测，也不据此修改产品实现。

## 本轮探针与复现边界

入口为 `eval_memory_e2e.production_sandbox_probe`：仅在全新 debug 目录生成合成文件、私有空 home、
原生配置与只读 RPC；不导入账号、认证、日常记忆或已有会话，不登录/退出任何账号。
这属于不调用模型的机制验证，不是以空账号替代用户当前账号做记忆成绩。
实际 UI canary 须在替代 OS 边界准入并核验原账号后另建批次。

```bash
"$MEMORY_E2E_PYTHON" -m eval_memory_e2e.production_sandbox_probe run \
  --output "$HOME/debug-workspace/e2e-evaluate/memory-e2e/astudio-production-native-policy-NEW"
```

该入口绝不生成应用启动租约、正式 Profile 或自动记忆准入。
输出包括受限工具原件、两种嵌套失败、后端 RPC、退出回执、制品摘要与合成文件保全。
旧实验和未知操作只保留观察，不用新结果覆盖。

## 仍符合约束的候选外层边界

Seatbelt 自身重入不能通过删除一层、替换内核或词法权限代理来绕过。
本轮接下来可检验的是**独立于原生 Seatbelt 的 OS 边界**，而不是降低访问拒绝要求。

### 候选一：无宿主共享的 macOS 虚拟机

在独立来宾系统内运行完全相同的生产包和原生沙箱；宿主数据不映射进来宾。
外层由独立 OS/虚拟化边界提供，不在生产进程上预先安装第二份 Seatbelt。
Apple 的 [Virtualization 示例](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)
与[共享目录文档](https://developer.apple.com/documentation/virtualization/shared-directories)提供该架构的依据；
这只是候选设计，当前没有运行 VM，不能宣称已验收。

具体准备/验收计划：

1. 使用 macOS ARM 来宾；仅复制生产包原件并核对签名、版本、ASAR/内核 SHA。
   本机 24GiB 内存、硬件虚拟化可用、约685GiB 可用磁盘；初始计划分配4 vCPU、8GiB RAM、80GiB虚拟磁盘。
   系统镜像尚未下载，未安装 VM 运行器；下载大小和实际资源以所选官方镜像为准。
2. 宿主共享目录、剪贴板、拖放、iCloud 文件同步和其他宿主数据桥均关闭；不能映射宿主 home。
   如需控制通道，只传入本单元执行材料和返回证据；不能让来宾任意读取宿主路径或其他单元。
   网络还须拒绝宿主地址/控制端口与其它来宾，只允许所需模型服务；仅声明 NAT 不足以准入。
3. 在生产客户端中登录当前同一个 AStudio 账号；不要求新账号，不复制宿主整份 home/钥匙串。
   GUI 发送仍使用真实桌面链路；guest 内核/工具、模型、原生权限及焦点均须在来宾重新证明。
4. 在宿主及旧 VM 存储创建完全合成的非目标/旧单元事实，先证明控制端可读，再验证来宾的
   读/stat/枚举/写/链接/工具后代均不能访问，区分 ENOENT 命名空间隔离与 EPERM 策略拒绝。
   旧 VM 磁盘不附加到新来宾。该边界不保护同一来宾内任意新增目录，因此来宾不能并存其它 Harness 或旧单元。
5. 保留无学习事实的账号基线。按“用例×重复”切换整台 VM 的独立基线克隆；轮内持续保留记忆，
   退出前等前台/后台空闲。三单元 A1→B1→A2 使用同一查询，验证后续单元不能读到旧值。
   账号云端来源仍须单独检查，不把新 VM 当作记忆冷启动证明。
6. 只有生产后台自动整理、产物读回、OS拒绝与单元切换均通过后才讨论正式评测；当前仍不启动20题。

该路线需要新增执行环境及客户端登录，须由用户确定是否采用；当前普通实例保持运行。

### 候选二：已有 Endpoint Security 的强制文件策略

Apple [Endpoint Security](https://developer.apple.com/documentation/endpointsecurity)支持对待发生事件授权，
需要相应 entitlement 和系统扩展。它与原生 Seatbelt 是不同机制，理论上可提供外层访问拒绝。
本机存在启用的 ManageEngine Protectord/Application Control 扩展，但**没有验证其当前配置可提供
覆盖文件读取/元数据/枚举/写入、后代进程及旧单元的不可绕过拒绝**；不能据安装状态准入。

没有读取/变更企业策略或连接管理控制台，也没有把“阻止应用执行”当作文件隔离。
若用户有可用的管理入口，先准备仅针对合成目录、精确生产进程及后代的策略并实测；
未取得覆盖证据前不动已有边界或安全软件配置。
