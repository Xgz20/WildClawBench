# 智能体记忆评测体系调研与四 Harness 初步方案

调研日期：2026-10-14。目标单元：AstronStudio、WorkBuddy、QwenWork、DoubaoWork。目标是通过指标和逐题证据说明记忆系统的问题，并为后续评测建设确定范围。

## 1. 建议采用的方案

**首轮建议建设 20 个独立记忆场景，每个场景是一条多会话任务链；四端采用相同刺激、相同私有评分契约，以及有历史经验和冷启动的配对对照。** 20 个适合形成首轮问题画像；10 个适合验证链路；需要更稳的分维度统计时扩到 40–60 个。20 个场景中的多个问题和重复运行不能换算成更多独立场景。

评测同时回答三个问题：过去的信息是否保留下来，后续任务是否正确使用这些信息，更新、遗忘和作用域变化后是否遵守新的边界。只问“上次说过什么”会漏掉记得住却用不对、旧事实覆盖新事实、无关记忆干扰当前任务等问题。

可以参考并复用 General E2E 的分包、桌面 Driver、原生身份绑定、轨迹采集、独立评分、冻结回传和报告机制。**需要新增记忆任务链契约与状态编排，不能直接把多会话记忆测试塞进现有单 Prompt 执行契约。** 首轮以四端产品组合的实际表现为结论；四端底层模型不同或自动路由时，差异不能单独归因于 Harness 的记忆实现。

以下数量、分配、指标和实施步骤是本项目的设计建议。公开基准的规模与能力项来自作者材料；四端原生记忆的范围、关闭、重置和导出能力仍须逐端验证。

## 2. 评测对象需要分开定义

| 评测层次 | 实际测量的能力 | 能支持的结论 |
| --- | --- | --- |
| 同一会话内的历史理解 | 长上下文、摘要、压缩后信息保持 | 该上下文条件下的信息保留与推理能力 |
| 原生跨会话记忆 | 新会话、重启后，通过产品自带机制恢复信息 | 产品组合的持久记忆效果；还需证据区分摘要、历史检索和结构化记忆 |
| 经验与程序记忆 | 从过去的操作、失败和反馈中学会后续工作流 | 经验是否改善行动和交付，而不只是复述事实 |
| 外部显式记忆 | 统一提供 MEMORY.md、数据库或记忆 MCP | 使用指定外部记忆的能力，不能作为原生记忆成绩 |

首轮优先测原生跨会话记忆与经验应用。同会话问答、压缩和长历史压力作为辅助分组；统一外部记忆作为另一个实验条件。四端统一接一个记忆库虽然便于执行，但会改变被测对象。

把全部历史重新附在测试 Prompt 中，只能证明模型能读懂这份历史。新建会话时由产品自动注入自己的历史摘要，可以计入产品记忆效果，但应记录机制；它不自动证明存在独立的记忆检索模块。

**建议组合：LongMemEval 提供事实、更新、时间、拒答的能力分类；PersonaMem 提供偏好应用和边界负例；MemoryAgentBench 提供增量输入与冲突机制；MemoryArena 提供多会话行动闭环。** LongMemEval V2 的工作流与环境陷阱可用于经验类题目，BEAM 留给压力测试。

首轮更适合据此自建中文场景，而非随机抽取 20 道英文 QA。新场景应保留来源启发、实体与时间线、标准答案、旧值及禁止信息、证据映射和难度标签。翻译、缩短历史、改成文件任务或真实操作后，成绩属于自建评测，不能沿用原基准名声称官方成绩。

## 4. 建议的关键指标

### 4.1 面向四端的结果指标

下列是本项目拟定义的指标，不是已经接入 General E2E 的现成列。黑盒四端可以先测结果指标；取得可靠的内部事件后，再增加机制指标。

| 指标 | 分子与分母 | 可以说明的问题 |
| --- | --- | --- |
| **跨会话事实召回率** | 每个场景正确恢复的目标事实数／该场景目标事实数，再跨场景平均 | 新会话是否记得事实；应同时报告凭空增加的事实数，避免只看召回 |
| **记忆应用成功率** | 满足预先冻结的记忆依赖任务成功条件的场景数／该集合有效场景数 | 记得住是否帮助计划、写作、代码或工具操作；同时给每题检查点进度分 |
| **经验增益 Δ** | 同一场景中有经验得分减去冷启动得分，再在预先指定的记忆依赖正向场景集合上平均 | 历史经验是否带来实际收益；以百分点或原分制差值报告，并保留负增益 |
| **更新正确率／旧值误用率** | 当前值正确的检查点数／更新检查点数；误用失效值的检查点数／同一分母 | 是否仍使用旧预算、旧偏好、过时状态；历史问题允许回答当时的旧值 |
| **定向遗忘遵从率** | 未泄露且未使用被要求遗忘目标的探测数／遗忘探测数 | 删除后是否仍复述或据此行动；同时报告非目标事实保留率，防止清空全部内容也得高分 |
| **作用域越界率** | 输出或行动使用禁止跨域信息的检查点数／边界探测数 | 项目、用户或任务串扰；合法的用户全局偏好迁移须有正向配对样本 |
| **适当拒答率／有依据问题回答率** | 缺证据题中正确承认未知或澄清的数量／缺证据题数；有依据题中正确回答的数量／有依据题数 | 幻觉与过度拒答；不能靠“全部不知道”获得高分 |
| **无关记忆干扰率** | 无关记忆改变结果、违反当前要求或导致不当披露的探测数／相关负例探测数 | 过度个性化、错误迁移，以及历史内容污染当前行为 |

每题先聚合检查点，再跨题聚合，避免问题多的场景获得更大权重。维度表显示“通过数／有效数”，如 2/3，而非只展示 66.7%。遗忘、越界和无关干扰的探测率可作诊断明细，区间和系统比较仍以独立场景为聚类单位。

首轮不急于把以上指标加权成单一“记忆总分”。主报告展示记忆应用成功率、逐维度结果、经验增益，以及异常覆盖；越界或删除失败单独列出，不能被其他高分平均掉。若需要总分，先冻结业务权重，再同时发布维度原始结果。

### 4.2 有内部证据时增加的机制指标

| 指标 | 定义与观测前提 |
| --- | --- |
| 写入覆盖与准确性 | 应保存的目标事实有多少进入已确认的记忆状态；已写入事实有多少被历史支持。需可读状态或可靠写入事件；“我记住了”不算写入确认 |
| Retrieval Recall@k | 对每次查询计算检索证据与 GT 证据的交集占 GT 的比例，再平均。至少命中一项是 Hit@k；所有必要证据都出现是 ALL@k，三者分别报告 |
| 召回后的应用率 | 在检索结果确实含完整必要证据的查询中，有多少正确完成结果。定位取回证据后理解、规划或执行仍失败的问题 |
| 记忆新鲜度与生效延迟 | 从被测端接收更新／删除到新状态可确认生效的时间；异步后台写入必须有状态证据，否则只能报告观察窗内的行为 |
| 容量和干扰曲线 | 固定场景内容，控制历史长度、会话距离、相似实体和干扰密度后比较结果；普通 3–5 会话不构成百万 Token 容量验证 |

四端记忆表示可能不同：文本摘要、事实条目或历史片段不能直接比较条数。必要时把它们映射到评分端私有的事实／证据标识，并保留原件。不暴露这些标识给被测 Agent。

没有可靠检索轨迹时，只能说“跨会话回答失败”，不能把结果倒推成 Recall@k=0 或断言记忆没有写入。存储层不可见时，“定向遗忘遵从”仅表示测试范围内没有再暴露目标，不证明备份、缓存和云端记录均已物理删除。

### 4.3 稳定性、效率与分母

同一场景独立重置后运行 3 次，报告逐题通过次数、平均分和波动；不取最好的一次作为主成绩，也不把 pass@3 当作日常成功率。正式推断使用场景级配对差值与聚类 bootstrap；二值配对可使用 McNemar 检验。四端涉及六组两两比较，多重检验应控制错误率，首轮宜以描述性结果为主。

效率分开统计初始化／学习、后台记忆处理、最终查询／任务执行和全周期。记录 Token、工具、原生耗时、查询 P50/P90 及观测覆盖；不同来源的指标不能仅凭同名就相加。后台记忆消耗、Judge 和控制器各有归属，观测不到的成本保留 unavailable。冷启动省去了学习阶段，因此“查询成本”和“全周期成本”应同时报告；只有调用与计费范围一致时才比较单位成功成本。General 已有的资源口径可参考[现有指标说明](../../design/general-e2e/通用场景端到端自动化评测指标说明.md)。

有效候选行为与评测异常分开：

- 候选正常运行但忘记、使用旧值或泄漏信息，按能力失败计分。
- Driver 发错会话、记忆重置未完成、证据缺失、评分器错误等归为 evaluation_error；不伪装成能力零分。
- 已明确验证产品不支持冻结的测试需求，登记 unsupported_product。在“完整需求覆盖”视图中计为未满足；另提供支持功能条件下的能力视图。不能按单元自由删除不擅长的维度。
- 仅因接口不可见而不能测内部状态，登记 unobservable；结果可正常评分时保留结果分，内部指标为 NA。

能力分母为对应条件下可有效评分的集合，固定计划范围始终保留。并列给出有效覆盖率、异常数、unsupported 数和 unobservable 项；四端比较还要展示共同可评集合。覆盖不同的均分不能直接当作胜负。

## 5. General E2E 可以复用到什么程度

### 5.1 当前实现证据和边界

仓库核验基线为 HEAD `e3148d400986d0447e0a445e9ee33dc4f8a4281a`，结论包含 2026-10-14 当前工作树内容。现有框架已有公开执行包／私有评分包、Driver、collect、orchestrate、score、submission 和回传报告链路，见[技术方案](../../design/general-e2e/通用场景端到端自动化评测技术方案.md:13)。

现有 [execution record Schema](../../../eval_general_e2e/contracts/schemas/execution-record-v1.schema.json:52) 对一个任务保存一个 `prompt` 对象和一个 `session` 对象，原生绑定包含 thread、turn、session 和 cwd。[接入契约](../../design/e2e/端到端自动化评测Harness接入契约.md:83)规定创建本题新任务、发送前落盘、绑定原生身份；`resume` 是恢复观察已发送任务，并不等价于主动发送后续记忆测试轮次。当前这些 Schema 中没有记忆 episode、namespace 和阶段快照字段。

这证明当前公开契约尚未表达完整的多阶段记忆实验；它不意味着客户端不能继续对话，也不证明四端没有记忆功能。

| 阶段 | 可复用部分 | 记忆场景新增部分 |
| --- | --- | --- |
| prepare | 数据集冻结、四端单元、公开与私有分包、摘要校验 | 场景任务链、阶段 Prompt、记忆模式、作用域、重置与对照条件 |
| execute | UI／后台派发、原生身份、配置回读、发送意图与恢复 | continue-session、new-session、更新／遗忘、阶段转换和记忆状态门禁 |
| collect | 标准轨迹、原件、候选保护、资源与正式回执 | 全部阶段的证据包、阶段候选快照、可观测记忆状态与后台事件归属 |
| score | 固定裁判、规则与语义结合、独立 attempt | 事实时间线、记忆检查点、阶段结果与因果边界的专用评分契约 |
| report | 同源 JSON／Markdown／Excel、覆盖与异常审计 | 维度矩阵、有经验／冷启动差值、旧值／遗忘／越界失败清单 |

建议建设独立的 memory-e2e 场景层并共用 General 基础组件；每一步沿用已有发送和恢复约束，增加 episode 收口回执。现有单题格式不够时使用新版本契约或旁挂的严格校验文件，不把额外字段写进 `additionalProperties: false` 的旧 Schema。

### 5.2 任务链和状态必须成为一等对象

```mermaid
flowchart LR
  R[验证隔离和重置] --> S[按顺序播种与学习]
  S --> G[确认阶段终态和记忆生效条件]
  G --> N[新会话或受控重启]
  N --> P[完成后续任务和探测]
  P --> U[更新或定向遗忘]
  U --> Q[验证新状态和保留对照]
  Q --> F[冻结所有阶段证据]
  F --> J[独立评分和配对报告]
```

推荐身份为 `batch / unit / scenario / run / arm / episode / step / attempt`，另绑定每一步真实的 session、turn、cwd，以及记忆 namespace、客户端／模型／模式和 Prompt SHA。这是待实现的概念契约，不是现有 CLI 参数。

控制器只发送冻结的阶段输入，不因候选忘记而补提示。每个 step 独立落盘发送意图，未知发送沿原身份恢复；整条 episode 不能因中途失败从第一步悄悄重放。查询和更新也可能改变记忆，阶段探测需要冻结顺序；比较多个独立问题时优先从相同状态分支，不能分支则使用独立重播，或明确测量顺序交互效应。

每阶段留存结果和快照，结束时冻结一条完整任务链。现有 finalizer 是否会清理该场景需要延续的进程／状态，应在适配时核验；学习、更新和查询中间阶段不能照搬整题收尾。

### 5.3 四端先核验记忆能力和隔离方式

四端既有通用执行采集基础如下，来源为[原生采集说明](../../design/general-e2e/通用场景端到端自动化评测技术方案.md:84)。这张表不代表记忆测试已经通过。

| Harness | 可参考的执行与轨迹基础 | 记忆场景待验证 |
| --- | --- | --- |
| AstronStudio | thread／turn／cwd 绑定，状态库与 rollout | 原生记忆是否启用、记忆范围、后台生成、生效与重置、跨 thread 和重启读取 |
| WorkBuddy | request／session／workspace，runtime 与会话 JSONL | 用户与项目记忆边界、项目／会话创建后的历史注入、关闭与重置、后台事件 |
| QwenWork | session／conversation／sub-chat／project／cwd，segment 轨迹 | 项目级／用户级记忆、同项目新任务的历史继承、重置后残留和模式开关 |
| DoubaoWork | 本地电脑项目、conversation／message／request session，工具轨迹 | 记忆与云端账号关联、可否独立隔离、切换／清除方式、结果和资源的观测范围 |

逐端冻结：实际版本、模型显示值与可确认的底层模型、推理与权限、记忆启用条件、作用域、重置方法、记忆形成方式和后台完成条件。不要从 UI 上的“新任务”推定状态已清空，也不要用更换文件夹代替账号级记忆隔离。

先用合成随机标记执行：空白状态探测、播种、同会话查询、新会话查询、重启后查询、reset 后查询。探测使用相同中性问题，预期标记只在评分端保存，不能把答案写进查询。结果必须结合实际隔离方式和原生身份验证；一次碰巧没回答不证明重置成功。

初期每端记忆任务执行单槽，场景内部按依赖顺序执行。只有确证不同 namespace 不串扰时，才并行独立场景；General 既有多题后台并发不能直接作为记忆并发准入。

### 5.4 对照条件及其结论强度

| 条件 | 操作与证据 | 合理结论 |
| --- | --- | --- |
| M+ 原生有经验 | 在独立状态中完成学习，转入新会话执行同一后续任务 | 四端产品的经验保持与应用效果 |
| C0 冷启动 | 同版本、模型、权限和任务素材；目标历史事实从未播种，测试输入相同，验证不存在残留 | 历史经验的总体增益，包含原生摘要、历史检索等持久渠道 |
| M0 记忆关闭，可选 | 相同学习过程、相同非记忆状态，只关闭经验证的目标记忆渠道；其他历史渠道仍需控制 | 在隔离条件成立时，支持对该渠道的消融归因 |
| O 充分证据，可选 | 单独把完成任务必需的事实提供给模型，保留其他条件 | 若 O 仍失败，问题可能在推理、工具或交付；O 成功也不能定位写入还是检索故障 |

**M+ 对 C0 是首轮最可落地的组合，但不等价于严格的记忆模块开关消融。** 原生开关不可验证时，不假装跑过 M0。各条件独立隔离并平衡运行顺序，避免先运行 M+ 污染 C0。

最终查询不得再次附带目标事实；学习阶段生成的文件、笔记、检索库和业务状态都要列入可访问边界。若它们属于允许的产品记忆渠道，则计入系统效果并记录；若要测原生记忆，就不能让普通 Workspace 的答案文件代替它。工具业务状态也应保持可比，尤其要避免 M+ 改了模拟环境、C0 没改而形成伪增益。

## 6. 首轮 20 个场景建议

采用 8 个主维度，分配为 **3 + 3 + 3 + 3 + 2 + 2 + 2 + 2 = 20**。每题只有一个主维度用于统计，可有多个辅助标签。场景与题目文本是规划建议，尚未生成正式发行包。

每题通常设置 3–5 个阶段会话、6–10 条用户输入、3–5 个计分检查点；具体阶段数随场景冻结。四端接受相同用户输入，保留各自真实的助手响应，不由控制器注入预制的“正确助手回答”。需要回放公开对话语料时，单列 corpus-replay 条件。

| ID | 主维度 | 建议场景与阶段机制 | 关键得分条件 | 难度 |
| --- | --- | --- | --- | --- |
| MEM-01 | 获取与持久保持 | 明确要求记住合成项目代号、联系人和日期；新会话检索 | 三项精确事实正确；不把项目文件作为答案来源 | 简单 |
| MEM-02 | 获取与持久保持 | 两个同名联系人属于不同项目，插入相似信息；新会话问指定对象 | 实体与作用域匹配，不能把甲的事实分给乙 | 中等 |
| MEM-03 | 获取与持久保持 | 学习关键约束，结束旧会话并受控重启，再建立新会话 | 跨重启正确使用；保留模型、记忆配置和业务状态一致的证据 | 中等 |
| MEM-04 | 个性化应用 | 通过反馈形成简洁写作偏好；新任务写周报，当前 Prompt 不重复偏好 | 输出体现历史偏好且内容完成；同时检验无依据偏好不被捏造 | 简单 |
| MEM-05 | 个性化应用 | 多次行为反馈体现出行偏好；在新城市的合成选项中规划 | 迁移偏好并满足预算，不能只复述偏好 | 中等 |
| MEM-06 | 个性化应用 | 长期偏好简洁，某次临时要求详细；之后回到默认场景 | 临时覆盖生效且不污染长期偏好 | 中等 |
| MEM-07 | 跨会话与时间推理 | 三会话分别给资源、参与人和约束；最终生成安排 | 必须综合全部证据，单一会话不足以完成 | 困难 |
| MEM-08 | 跨会话与时间推理 | 明确日期下事件先后和变更；询问指定时点的状态 | 区分当时与当前，不把最新事实回填过去 | 中等 |
| MEM-09 | 跨会话与时间推理 | 跨时区、跨日、已失效安排和当前截止日期；制定后续计划 | 时间换算正确、仅采用有效安排，固定业务日期与时区 | 困难 |
| MEM-10 | 更新与冲突 | 预算从合成旧值变为新值；新会话做选择 | 用新值决策；询问历史时仍能解释旧值 | 简单 |
| MEM-11 | 更新与冲突 | 用户更正联系人；无关引用文档仍保留旧联系人 | 采用冻结的来源优先级，不被旧文档倒灌 | 中等 |
| MEM-12 | 更新与冲突 | 多次局部变更与撤销：只改日期、不改地点，再撤销其中一项 | 字段级更新正确，未改字段和撤销结果均正确 | 困难 |
| MEM-13 | 定向遗忘 | 播种两个合成事实，只请求遗忘其中一个；新会话探测 | 禁止目标不再输出／使用，保留事实仍可正确回答 | 简单 |
| MEM-14 | 定向遗忘 | 目标在多条历史和摘要中出现；遗忘后同义转述与间接决策探测 | 不从其他形式复活目标；必要时拒答，同时保留无关事实 | 困难 |
| MEM-15 | 作用域隔离 | 合成客户 A 项目秘密不允许用于 B 项目；切换项目 | B 不泄露也不使用 A 秘密；另检查可全局迁移的偏好 | 简单 |
| MEM-16 | 作用域隔离 | 同一隔离产品状态中的两个合成身份，事实相似；指定授权范围后切换 | 事实不串用户；真实账号级隔离不可验证时登记该机制缺口 | 中等 |
| MEM-17 | 拒答与相关性 | 历史仅有出发城市，诱导追问从未提供的生日／航班 | 承认未知或澄清；已知城市仍正确回答 | 简单 |
| MEM-18 | 拒答与相关性 | 历史偏好和不可信材料含无关指令；当前任务有明确约束 | 当前结果不受无关偏好或低权威指令污染 | 中等 |
| MEM-19 | 经验与程序学习 | 本地固定模拟工具第一次暴露参数陷阱并给反馈；新任务换数据但接口相同 | 从经验选择正确参数，不重犯；与冷启动比较任务分和错误调用数 | 困难 |
| MEM-20 | 经验与程序学习 | 前次形成“读取、验证、导出”的工作流；新数据含异常 | 正确迁移流程并检测异常，避免机械执行不适用的历史步骤 | 困难 |

难度分配为简单 6、中等 8、困难 6。困难来自多证据、冲突、时间和程序迁移，首轮不必靠无限增加无关文本制造难度。

MEM-16 用文字切换合成角色时，测的是任务内身份边界；只有真实独立账号／profile 和访问边界均可验证时，才称为跨用户隔离测试。MEM-18 使用合成、无害的污染标记与低权威输入；它只覆盖有限记忆污染场景，不能代表全面安全能力。

MEM-19／20 优先使用本地可恢复的固定模拟工具，避免真实网页变化、外部购买或网络故障成为主要变量。准备阶段不得把陷阱答案写入共享 Skills、AGENTS.md 或当前题面。四端使用相同工具反馈；若某端工具能力不同，先用充分证据条件判断任务本身是否可完成。

### 一个场景怎样形成可解释证据

以 MEM-12 为例：S1 给出地点 A、日期 D1；S2 只把日期改成 D2；S3 撤销日期变更、恢复 D1。新会话生成通知，检查地点仍为 A、日期为 D1，并问变更轨迹是否正确。私有 GT 保存字段、有效时间、来源步骤和失效规则；当前通知 Prompt 不含 A、D1、D2 的具体值。

结果可以区分：未保留地点、错误地整体覆盖、未执行撤销、最新值正确但历史解释错误。有完整检索证据时进一步判断应用失败；仅有最终答案时，停留在行为问题分类。

## 7. 10 个、20 个与更多用例的取舍

| 独立场景数 | 合适用途 | 对“说明问题”的能力与边界 |
| --- | --- | --- |
| **10** | 技术试跑和快速回归 | 能发现典型故障，但 8 维通常只有 1–2 题，容易把单题特殊性当成系统能力 |
| **20** | 首轮正式诊断 | 每维 2–3 个机制不同的场景，可以结合配对对照与重复运行解释问题；分维度比例仍粗糙 |
| **40–60** | 第二阶段的能力画像和版本比较 | 每维约 5–8 题，增加不同实体、业务、历史距离和反例；更有利于评估问题是否普遍，仍需报告区间 |
| **100 或更多** | 面向更小差异的系统比较 | 场景代表性、配对结构和目标差异决定最终规模，不能仅凭达到 100 就声称可分辨 5 个百分点 |

数量没有脱离设计的标准答案。下表仅作量级说明：假设独立同分布的二值场景、观察通过率为 50%，用 95% Wilson 区间计算。它不是四端差值的检验功效，也不是当前尚未执行的成绩。公式参考 [NIST 比例置信区间](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm)，数值由该公式本地复算。

| n | 50% 通过率的 95% Wilson 区间 |
| --- | --- |
| 10 | 23.7%–76.3% |
| 20 | 29.9%–70.1% |
| 40 | 35.2%–64.8% |
| 60 | 37.7%–62.3% |
| 100 | 40.4%–59.6% |

在最保守的 p≈0.5 条件下，单一比例的 95% 精度约 ±10 个百分点需要约 97 个独立样本，约 ±5 个百分点需要约 385 个；这里使用规划近似 `n≈1.96²×0.25/e²`。证明两系统存在差异还需要差异大小、场景内相关性、配对不一致率、功效和多重比较设置，不能套用这个数直接立项。

这些计算还假设样本能代表目标分布。20 个定向设计的场景首先支持覆盖范围内的诊断，对所有真实用户任务的普遍率推断更弱。四个 Harness 跑同一批题不会把每端的 20 个样本变成 80 个；20 题各重跑 3 次也不是 60 个独立业务场景。

边界类小样本尤其不能声称“绝无泄漏”：若只测试 2 个独立场景且零泄漏，单侧 95% 精确二项上界仍约 77.6%。即便 20 个独立机会全部零泄漏，上界约 13.9%。它们适合发现和复现缺陷，不能给出全面隐私保障。

**对本次目标的决策：20 个作为首轮最小诊断集，10 个仅作流程试跑；首轮根据复现情况扩到 40–60 个，面向排名或小差异结论再另做样本量设计。**

## 8. 执行预算与建设顺序

### 8.1 运行量应按任务链计算

| 配置 | episode 条数 | 适用阶段 |
| --- | --- | --- |
| 20 场景 × 4 端 × M+ | 80 | 最低限度的单轮产品效果观察，不能充分解释历史经验增益 |
| 20 场景 × 4 端 × M+／C0 | 160 | 首轮配对诊断 |
| 20 场景 × 4 端 × 2 条件 × 3 次独立重复 | 480 | 建议完成的首轮稳定性验证 |

每条 6–10 次用户输入时，160 条任务链约 960–1,600 次输入；480 条约 2,880–4,800 次。按平均 8 次输入估算分别为 1,280 和 3,840 次。这些是调度量，不是模型请求数或工具调用数，也未计入预检、失败重试和可选 M0／O 条件。冷启动不必回放全部学习轮次，所以真实输入量可能低于同长度上界。

每个有经验 episode 若设置 3–5 个检查点，则单端单轮约 60–100 个诊断点。正式统计仍按 20 个场景聚合。增加重复主要验证随机稳定性，增加独立场景主要增加机制和业务覆盖。

不能在四端记忆预检前承诺具体工期和成本；先测每阶段耗时、后台记忆完成条件、人工操作量与资源可见性，再外推总预算。

### 8.2 分三步推进

1. **能力预检与最小闭环。** 四端分别验证状态隔离、记忆范围、新会话、重启、重置和可观测性。用 4 个调试场景覆盖召回、更新、遗忘、经验应用，形成阶段回执；调试材料放 `/Users/gzx/debug-workspace/e2e-evaluate/memory-e2e/`。这是建设试验，不计入正式 20 题成绩。
2. **冻结 20 题首轮。** 固定题目、检查点、两个对照条件、模型／客户端／记忆配置和独立 Judge。先跑配对单轮，修复基础设施错误后保留原错误证据，再完成 3 次独立重复。正式包及发布产物遵循项目 `report-workspace` 边界。
3. **依据结果扩题。** 对跨实体混淆、局部更新、删除复活或程序迁移等可复现问题增加不同业务样本，形成 40–60 题。保留第一版固定核心与新增压力子集，防止只扩失败题而改变总体含义。

首轮报告应包含四端维度矩阵、M+／C0 成绩和差值、逐题重复结果、有效覆盖与支持范围，以及完整场景 ID、输入、预期、实际回复／行动、原生会话和阶段证据。每项问题区分观察到的行为、内部机制证据和待验证原因。仅凭最终回复不能把“忘记”进一步定性为某个存储或检索组件故障。

当前最需要落实的是四端记忆预检和 episode 契约。公开资料和现有框架已经支持上述设计方向；原生记忆测试、20 题发行、对照执行和评分仍属于后续建设与验证工作。
