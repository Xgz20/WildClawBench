## 1. 结论与评测决策

**应先完成客户端记忆能力核验，再执行正式记忆评测。四端都有记忆相关能力，但启用条件、学习时机、信息组织方式和淘汰策略不同，不能统一采用“发送历史 → 等待 10 秒 → 新会话提问 → 清空后进入下一题”。**

- **AStudio：内核支持跨会话长期记忆，源码默认关闭。** 已安装版本为 3.5.0，内核为 ACode 1.0.5-rc.3。本次读取的来源配置和桌面 overlay 配置均没有开启记忆的配置项；尚未取得运行中实例的有效特性快照和记忆流水线成功证据，因此暂不能认定本机已经启用。默认历史候选需要空闲 6 小时。内核有重置接口，桌面未发现对应管理入口。[A1–A4]
- **WorkBuddy：产品明确支持自动记忆、主动维护和清空。** 5.5.6 当前“生成对话记忆”开关开启；官方说明每晚整理历史、重建摘要。打包代码包含重置实现，但当前空摘要状态只显示导入，未显示重置按钮。需要区分记忆画像和历史对话检索。[W1–W4]
- **QwenWork：记忆管理和本地状态最容易核验。** 1.2.5 当前意识模式、自动记忆均开启，支持用户画像、长期记忆、按天记录的短期记忆、本地索引及反思整理。“清空记忆”有明确文件范围，但不等于重置整个意识系统。[Q1–Q4]
- **DoubaoWork：同时支持主动记忆和自动提炼。** 2.31.10 当前记忆开启，已只读打开菜单，确认有“删除全部记忆”。可见列表仅展示主动记忆；自动提炼内容不能靠这个列表验空。官方 FAQ 明确删除并非立即停止被引用。[D1–D3]
- **Codex（补充参考）：桌面已有主机级总开关、工具会话学习控制和删除入口。** 截图中所选主机为 Local，两个开关均开启；源码默认关闭与用户当前开启状态并不矛盾。所核验源码支持默认 v1、可选 v2 和双写，使用次数与未使用窗口影响整理选材。桌面删除与内核 reset 的证据范围分别列明，不能只删除 `MEMORY.md` 就认定完全重置。[C1–C7]

**手动删除只是记忆淘汰策略的一种。** 淘汰还可能由访问频率、未使用时间、容量压力、重要性或内容过时触发。应分别评测自动淘汰、主动遗忘和环境重置，不能用一次清空操作替代全部遗忘能力测试。

本文没有发送新的评测提示词、修改记忆开关、导入记忆、执行清空或删除操作。此前 WorkBuddy 冷启动查询仅保留为框架调试记录，不作为本报告的记忆能力结论。现有账号含日常使用状态，本文提供重置方案，不将“允许使用当前账号”解释为可以清空其全部日常记忆。

术语按用途区分：

- **会话上下文**：当前会话已带入的消息和工具结果。删除长期记忆不会自动从当前上下文中抹去它们。
- **跨会话记忆**：产品在新会话中自动带入或检索的持久信息。
- **短期记忆文件**：如 QwenWork 按天保存的摘要，虽然叫“短期”，仍可跨会话存在，不能与模型上下文窗口等同。
- **程序／经验记忆**：可复用的操作规则、环境经验和技能。与用户事实、偏好分别统计。
- **淘汰**：信息被降权、退出默认注入、移出活跃记忆或被删除。必须注明发生在哪一层，不能全部称为物理删除。

## 4. 各客户端的实现与开关边界

### 4.1 AStudio：默认关闭的内核能力，重置需要同时处理文件与数据库

指定会话的原报告分析了较早桌面锁定的内核版本。本次根据安装清单补查了与本机版本号对应的 `v1.0.5-rc.3` 源码标签，避免直接将旧版本结论套到安装包。版本号对应不等于已证明二进制与源码逐字节一致。[A1、A2]

可见链路为：有输入的 `turn/start` 触发后台任务，从符合条件的历史会话抽取 raw memory 与 rollout summary；再通过整理 Agent 更新长期摘要等产物；后续会话将摘要和使用指引作为 developer policy 带入。它不是“当前回答结束就保证长期记住”。候选排除当前触发线程，默认空闲门槛 6 小时、历史年龄窗口 10 天、单次最多领取 2 个会话；还受线程资格、存储模式、数据库和模型服务条件约束。[A2]

| 配置／接口 | 控制范围与限制 |
| --- | --- |
| `features.memories` | 总开关，源码默认 false；控制记忆扩展与后台启动路径 |
| `memories.generate_memories` | 默认 true；影响线程能否成为学习候选，不保证阻止其他已允许的旧线程被整理 |
| `memories.use_memories` | 默认 true；与总开关共同控制摘要／指引注入 |
| `memories.dedicated_tools` | 默认 false；决定专用记忆工具是否暴露，不决定全部摘要注入 |
| `thread/memoryMode/set` | 调整某线程后续学习资格；不是清空已形成记忆 |
| `memory/reset` | 实验性 app-server 接口；重置数据库中的记忆阶段数据，再清理记忆根目录 |

显式记忆存在 `add_ad_hoc_note` 工具路径，但取决于总开关、使用开关和专用工具配置。工具执行成功与后续整理、检索、使用成功应分别取证。桌面的 Recap 只是会话摘要展示，不能当作长期记忆总开关。[A1、A2]

本机已读的 `/Users/gzx/.acode/config.toml`、`/Users/gzx/.acode/acode/acode-home-overlay/config.toml` 均未发现记忆配置；已观察到的内核启动参数也没有记忆覆盖项。这支持“按默认应关闭”的判断，但没有替代运行实例有效配置核验。overlay 下存在记忆目录，也不证明生成或使用成功。本次没有修改配置或启用该功能。[A3]

**清除范围：** `memory/reset` 清除 SQLite 的阶段结果和记忆任务数据，随后清理实际 `CODEX_HOME` 下的 `memories`、`memories_extensions` 内容。源码也有 `debug clear-memories` 路径。清除不删除历史会话，不改变它们的 memory mode；这些历史以后仍可能再次进入学习候选。清理根目录遇到符号链接会拒绝，不能把某个猜测目录的手动删除当作完整 reset。[A4]

**对评测的影响：** 先确认实际 home、有效开关、抽取／整理模型配置与成功证据。默认跨会话学习需要按时间编排；缩短门槛属于另一种配置条件，应单独命名。仅关闭 `generate_memories` 不能构造可靠的全局无记忆对照；仅删 Markdown 也不能构造可靠的冷启动环境。

### 4.2 WorkBuddy：每晚整理、画像维护与历史检索需要分别取证

官方说明会从历史会话整理可复用的事实和偏好，每晚更新摘要，再将相关信息用于后续请求；同时支持历史对话检索。主动维护可通过编辑建议对话或导入完成，后台处理是否完成需要另行观察。[W1]

5.5.6 的安装包将这些操作接到 daemon feature：`memoryGetProfile`、`memorySaveSettings`、`memorySubmitSuggestion`、`memoryImportContent`、`memoryCheckUpdating`、`memoryClearProfile`。管理 UI 处理重置确认、成功／失败与更新状态。本次没有调用修改类接口；这条静态链路也不足以说明后端使用了哪种数据库或向量检索算法。[W3、W4]

当前 UI 只显示开关、管理说明和导入。安装包中 `MemoryManageInline` 仅在成功读取且存在非空内容时显示重置和编辑按钮；因此当前看不到清空按钮，不能据此判断产品不支持清空。代码还包含“本地记忆”设置，但在 WorkBuddy local mode 下隐藏，不将该共享组件字段当作本机可用的独立开关。[W2、W4]

**清除范围：** 产品提供清空当前记忆画像的操作。官方说明关闭会停止新提取，关闭或删除后对应记忆不再用于后续对话；但未在已核验材料中证明该操作同时删除全部历史对话及其检索状态。画像清空、历史检索不可用和后台不再重建画像，应分别验证。[W1、W3]

**对评测的影响：** 自动记忆按每晚整理契约安排训练和查询；不要因发送后 10 秒尚无新摘要就判定记忆失败。主动建议／导入是另外的输入条件。若测试信息仍可从历史对话检索获得，应将成功标注为产品历史恢复能力，不能只归因于清空前的画像存储。

### 4.3 QwenWork：本地分层记忆与反思淘汰，自动开关不等于完全停用

当前界面展示的主目录为 `~/.qwenworkcn/awareness/main`。`USER.md` 保存画像，`MEMORY.md` 保存长期知识，`memory/` 保存按天摘要；`SOUL.md`、`AGENTS.md` 分别承担协作风格与工作规范。另有语音记忆、索引、目录导入导出入口。[Q1、Q2]

安装包中的 `AwarenessManager` 将画像、长期条目及受预算限制的近期日志组装为上下文；`memory` 工具面向 user、memory、daily 三类目标，支持新增、替换和删除；`memory_search`／`memory_get` 处理本地记忆检索和读取。所核验的 `MemorySearchService` 建立的是记忆文件索引，不能因某段工具说明提到历史回忆，就断言它直接索引全部原始会话。[Q3]

两个开关具有不同含义：

- **意识模式**影响记忆系统、个性化及技能进化的总体启用条件；作为消融会同时改变多个因素。
- **自动记忆**映射到自动／手动维护模式，限制自动 sink 和反思。`isMemoryEffectivelyEnabled()` 仍取决于意识模式，记忆工具定义也依赖该条件，因此仅关自动维护不能证明全部记忆工具或读取已关闭。[Q3、Q4]

**清除范围：** 主进程 `awarenessRouter.clearMemory` 删除 `USER.md`、`MEMORY.md` 和 `memory/` 下普通文件，重新创建空的两个主文件，再重建本地索引。它没有在该操作中重置协作风格、工作手册、技能或全部反思元数据；语音记忆也没有作为独立目标显式出现在这段删除代码中。界面为风格和工作手册提供了独立重置按钮。[Q2、Q3]

只读界面还显示长期记忆约 9.9 KB、使用率 99%，已有记忆趋势和历史记录。这是当前账号不是空白基线的直接证据；不能据此断言一定发生了淘汰，也不能将后续新增失败直接归为召回问题。[Q2]

**对评测的影响：** 该端适合用文件元数据、条目变更、索引和工具返回辅助行为评测。清空后应从新会话验证；同会话已注入内容仍可能存在。经验类任务还应固定工作手册、风格和 Skills 基线，否则清空事实记忆后仍可能保留已学到的操作经验。

### 4.4 DoubaoWork：主动记忆可见，自动记忆不是列表的全集

当前管理页明确说明同时保存用户要求记住的信息、自动提炼对话内容，列表只展示前者。只读展开右上角菜单后，可见“删除全部记忆”。客户端打开的“了解更多”指向官方记忆 FAQ。[D1、D2]

FAQ 将两条路径区分为：自动提炼按周期刷新，主动记忆按指令更新；主动记忆满额时，最近保存的信息覆盖最早保存的信息。记忆会作为后续生成的背景，但当前资料不足以确认后端是否采用向量检索、知识图谱或何种存储实现。[D3]

**开关与清除：** FAQ 说明关闭后停止使用和更新记忆，未删除内容在重新开启后可以恢复被参考；删除聊天记录不等于删除记忆。支持单条和全部删除，但删除后停止影响回答有延迟；保持开关开启还会继续形成新记忆。FAQ 为豆包通用说明，具体端场景以呈现为准；本机确认了开关和删除全部入口，完整删除范围及延迟尚未通过操作验证。[D2、D3]

**对评测的影响：** 主动记忆和自动提炼分别成组；列表空白只能用于判断没有可见主动条目。删除后不能立即宣称冷启动，也不能在开关关闭时测得“不再回答旧事实”就认定删除成功；需要在正确实验条件下验证重新开启后的行为。自动记忆的内部检索与写入证据不可得时，只报告行为层效果。

### 4.5 Codex：按主机管理的本地长期记忆，后台生成与读取分别受控

**客户端入口与作用域。** 用户截图中的“设置 → 个性化 → Codex 记忆”选择了“本地主机”，并显示两个已开启的开关：“启用 Codex 记忆功能”“允许从使用工具的聊天中生成记忆”；另有“删除 Codex 记忆”，文案明确指向 Local 上全部 Codex 记忆。OpenAI 官方说明确认这些控制按所选主机生效，聊天级 `/memories` 可分别控制当前聊天使用既有记忆及参与后续生成。它与 ChatGPT 网页记忆是不同存储；截图下方的写作风格控制也应另行记录。[C1]

本机桌面 bundle 标识为 `com.openai.codex`，版本 26.1007.71326，随包 CLI 报告 `0.162.0-alpha.17.2`。以下实现分析锚定本地源码提交 `669449b02c4b58de4bcd22485eb60c98a6e38a54`，不是安装二进制与该提交完全一致的证明；也没有据截图推断本机实际选择了 v1 还是 v2。[C2]

**开关与生成资格。** 源码中 `features.memories` 为 Stable，但默认值仍是 false；这是实现默认值，不能覆盖截图展示的用户选择。核心配置如下：[C3]

| 配置／控制 | 作用及评测边界 |
| --- | --- |
| `features.memories` | 总开关；控制后台流水线与记忆扩展 |
| `memories.generate_memories` | 默认 true；影响新聊天参与后续记忆生成的资格，不是阻止所有旧聊天继续参与生成的总停止按钮 |
| `memories.use_memories` | 默认 true；与总开关共同控制已有摘要和使用指引注入 |
| `memories.disable_on_external_context` | 默认 false；设为 true 时，检测到外部上下文后将源线程标记为 polluted；旧键 `no_memories_if_mcp_or_web_search` 为兼容别名 |
| `memories.dedicated_tools` | 默认 false；控制专用 list／read／search／add_ad_hoc_note 工具；没有专用工具仍可能经摘要与一般文件工具使用记忆 |
| `memories.version`／`dual_write` | 默认 v1／false；控制读写版本及是否同时生成两版 |
| 聊天级 `/memories`／`thread/memoryMode/set` | 聊天级使用与生成选择；线程学习资格调整不等于删除已形成的全部记忆 |

“允许从使用工具的聊天中生成记忆”在产品语义上控制工具会话的学习资格；关闭意味着不允许这类会话贡献新记忆，**不等于禁止使用工具或关闭全部记忆读取**。对应内核能力是外部上下文排除：当前源码检测 WebSearch、ToolSearch 等响应事件并更新线程资格。桌面开关的具体 RPC／配置写入链路未在本次核验，不能仅凭语义对应宣称已追踪到完整桌面调用链。[C1、C3]

**自动生成与使用。** app-server 在有输入的新 turn 实际启动、且主执行环境已配置后触发后台记忆任务；排除 ephemeral、非 root 来源等情况，再检查数据库与额度。默认候选需空闲 6 小时，历史年龄窗口 10 天，单次最多处理 2 个历史聊天，排除当前触发聊天。Phase 1 过滤历史并脱敏，调用模型抽取；Phase 2 选择材料、同步文件，并由整合代理更新产物。默认还有 Phase 2 成功后的 6 小时冷却条件；达到空闲门槛不代表马上完成整合。[C4]

读取侧在新会话中注入所选版本的 `memory_summary.md` 与使用指引，摘要按 2500 token 截断，细节按需检索。它属于跨会话长期记忆；当前聊天上下文、会话压缩和输入历史是另外的状态机制，不与这一摘要存储混成同一层。[C5]

| 实现维度 | 默认 v1 | 可选 v2 |
| --- | --- | --- |
| 文件根目录 | `CODEX_HOME/memories/` | `CODEX_HOME/memories_v2/` |
| 记忆阶段数据库 | `memories_1.sqlite` | `memories_v2_1.sqlite`；数据库位置以有效 SQLite 配置为准 |
| 单会话抽取 | raw memory、rollout summary、slug | summary、slug；summary 脱敏后按 9000 字节截断，不生成 raw memory 内容 |
| 整合产物与检索 | `memory_summary.md`、`MEMORY.md`、`raw_memories.md`、rollout summaries，可选 skills | rollout summaries 与 `memory_summary.md`；不要求生成 `MEMORY.md`／`raw_memories.md`，读提示直接路由到 summaries |
| 画像与经验 | 可在摘要／登记簿中组织用户偏好、环境经验和工作流 | 摘要组织用户资料、偏好与历史工作入口；不因缺少独立 `USER.md` 就判定没有画像 |

`dual_write=true` 同时运行两版独立的阶段结果、任务与租约；读取只使用 `version` 选中的一版，v2 摘要缺失时不回退到 v1。切换配置也不会让已有线程随意切换读取目录，正式对照应从新线程开始。双写不是双路检索，也不应当作成本相同的单写条件。[C3–C5]

**用户主动记忆。** 读提示要求只有用户明确请求才提交更新便签，默认写入所选根目录的 `extensions/ad_hoc/notes/`；启用专用工具时存在 `add_ad_hoc_note` 实现。后台从历史自动提炼与响应用户请求写便签是两条路径。便签创建成功仅证明输入已保存，不能直接推定所有长期摘要已即时更新。`AGENTS.md` 则承担显式指令，与生成的经验记忆分别管理。[C5]

**删除与重置。** 官方说明桌面删除重置所选主机的记忆存储；在本地主机且电脑历史记录功能可用时，还会清除 Computer History。这个桌面层附带范围来自官方产品说明，不能从开源内核的 reset 方法单独推导。[C1]

内核 `memory/reset` 先清除 v1 和已存在的 v2 记忆数据库阶段数据，再清理 `memories/`、`memories_v2/`、`memories_extensions/` 内容；有符号链接根目录时拒绝清理。它不在该方法中删除原始聊天或修改全部源线程的学习资格，也不删除 home 根的 `AGENTS.md`。旧聊天以后仍可能重新贡献记忆，运行中会话也可能已带入旧摘要。因此，桌面删除成功、两版存储清理、Computer History 清理和新会话验收应分别取证，不能靠当前聊天“似乎忘了”验收。[C7]

**与 AStudio 的差异。** 本文核验的 AStudio 内核 1.0.5-rc.3 使用较早实现，记忆 feature 标为 Experimental；Codex 所核验提交已标为 Stable，并有 v1／v2 与双写实现。Codex 截图还明确提供主机级桌面管理入口。两者共享部分两阶段设计，仍须分别确认实际版本、有效开关、模型服务与 home，不能以 Codex 已启用替代 AStudio 的就绪证明。[A2、C1–C4]

## 5. 记忆淘汰策略：频率、时间、容量与主动清理

| 策略维度 | AStudio | WorkBuddy | QwenWork | DoubaoWork | Codex（参考） |
| --- | --- | --- | --- | --- | --- |
| 访问频率／使用次数 | 阶段结果有 `usage_count`；Phase 2 输入优先按次数排序 | 未核实公开策略 | 已检查的硬淘汰按重要性、创建时间排序；未确认基于访问频率 | 未核实公开策略 | 解析引用后累计 usage_count；不等于所有文件访问次数 |

| 用户主动清理 | note／文件维护与全局 reset 是不同范围 | 修改建议、删除／重置画像 | 工具删除条目与 UI 全局清空 | 对话遗忘、单条／全部删除 | 显式更新便签与桌面／内核全局 reset 分开 |

### 5.1 AStudio：使用计数与未使用窗口作用于阶段结果

`record_stage1_output_usage` 为被引用的阶段结果更新使用计数和最后使用时间。`get_phase2_input_selection` 在未使用窗口内优先选择使用次数多、最近使用的结果；未使用过的结果以来源更新时间兜底。默认 30 天是未使用窗口，不是“所有记忆创建 30 天后统一删除”。[A5]

`prune_stage1_outputs_for_retention` 只清理符合条件且 `selected_for_phase2=0` 的旧阶段行；已选择结果退出后续输入，会通过文件差异传递给整理过程。因此，数据库阶段行淘汰、整理输入退出、最终摘要中事实消失是不同事件，不能仅根据 30 天参数推断用户层已经忘记某条事实。[A5]

### 5.2 QwenWork：重要性与年龄驱动的容量淘汰

安装包代码为记忆设置 critical、normal、low 等重要性。反思先尝试合并、压缩和删除低价值项；硬淘汰先处理 low，再处理 normal，同组按创建时间从早到晚排序，critical 仅在更高容量压力下允许处理。这不是访问频率驱动的 LFU，也不能直接称为 LRU。[Q4]

本机代码中长期记忆与画像的默认字节预算分别为 10 KiB、4 KiB。反思的运行判定含内容变更检查、1 小时最小间隔，以及 24 小时或使用率超过 80% 的条件；进入反思后的硬淘汰调用使用 70% 目标占用、95% 的 critical 处理阈值，并有结果校验／回滚路径。这些是静态条件，不是保证每小时或达到阈值就立即执行的时间承诺。[Q3、Q4]

近期日志默认只抽取有限数量的近期文件／块放入上下文，另有字节预算。**退出默认注入范围不等于日志从磁盘删除**；仍有可能通过记忆检索找回，必须分层记录。[Q3]

### 5.3 对未知策略的处理

WorkBuddy 目前只能确认周期整理、主动维护和清空，不能据此补写频率淘汰、指数衰减或容量算法。DoubaoWork 已知的满额覆盖说明针对主动记忆，不能推广成自动提炼记忆的全部后端规则。未公开不等于不支持；应标“策略未核实”，再用受控实验观察行为。

### 5.4 Codex：引用反馈驱动选材，时间窗口与内容更新共同作用

Codex 在解析记忆引用后，以引用中的源线程 ID 回写 `usage_count` 与 `last_usage`，Phase 2 优先按使用次数及最近使用情况选材。这里统计的是**可解析引用带来的反馈**，不能等同于每次文件读取或全部真实使用次数。[C6]

默认 `max_unused_days=30` 用于整理输入资格判断；从未被引用过的材料以 `source_updated_at` 兜底。后台只直接清理 `selected_for_phase2=0` 且超期的阶段行；已选结果退出后续选材，通过输入文件差异影响摘要重整。默认 top-256 上限、摘要预算、过时内容合并与来源删除一起影响最终保留内容，未发现可据此宣称统一指数衰减公式或逐事实 LRU／LFU 的依据。[C3、C6]

v2 整合提示要求新修正覆盖旧说法，移除仅由已删除来源支持的声明；这是提示契约，实际遵循情况仍需实验。应分别测量“进入下一轮整理的比例、文件中留存比例、被检索比例、行为中仍使用的比例”，避免将退出整理输入当作事实已被完全遗忘。用户主动删除／全局 reset 则单列为主动清理策略。[C4、C6、C7]

## 6. 将清除能力用于环境重置，需要补哪些条件

**可以利用产品清除入口降低重置成本，但清除完成只是重置的一部分。** 至少需要区分：清除操作返回成功、目标存储验空、索引／缓存更新、既有会话上下文退出，以及旧历史不会再次生成目标记忆。

| Harness | 建议的重置路径 | 必须另外固定或核验的状态 |
| --- | --- | --- |
| AStudio | 在确认实际 home 后使用内核 reset；隔离 home 比手动删目录可靠 | 历史线程资格、后台任务、阶段库、记忆根、后续新线程配置；避免旧线程重新抽取 |
| WorkBuddy | 有可见画像时走管理页重置，确认更新不在处理中 | 画像是否清空、历史对话检索、后台重建时机；当前空画像状态也需记账 |
| QwenWork | UI 清空事实记忆并观察空文件与索引；新会话开始 | 风格、工作手册、技能、反思元数据、语音记忆；不能只清两个文件 |
| DoubaoWork | 通过管理页删除目标记忆或全部记忆，等待生效再验证 | 可见主动列表之外的自动提炼状态、删除传播延迟、重新生成；暂无完整状态导出证据 |
| Codex（参考） | 按目标主机使用桌面删除；需要内核层重置时核验两个版本及有效存储位置 | 主机身份、v1／v2／双写、源线程学习资格、后台任务、Computer History 附带范围；用新线程验收 |

后续适配器可采用以下状态契约，属于建议，本文没有修改现有代码：

1. **记录基线**：客户端／内核／模型、账号匿名标识、记忆开关、作用域、已有记忆规模和相关配置指纹。
2. **确定清除范围**：区分单个测试事实、画像、记忆日志、索引、技能与全部账号状态；仅在已获授权范围内执行。
3. **避免重写竞态**：能够暂停生成的先暂停；记录后台任务和更新状态。未确认任务结束，不能仅凭一次成功提示进入下一题。
4. **执行并验收**：保留 UI／原生操作回执；可观察时核验目标文件、索引及更新状态；记录 `reset_requested_at`、`reset_completed_at`、`reset_verified_at`。
5. **从新会话验证**：避免继续沿用已含训练材料的上下文。在记忆功能处于本轮要求的状态下检查残留，不能用关闭读取掩盖删除未生效。
6. **满足学习条件后再查询**：记录写入／整理完成或约定的产品等待窗口；随后冻结该次条件和证据，再执行测试。

在当前日常账号下，如无法安全恢复原有状态，就不能宣称建立了“全新用户冷启动”。可以先做带随机档案标识的配对探测和测试事实级清理，但档案名只是逻辑标记，不是产品强制隔离。没有可靠 reset 时，报告应明确这是有既有记忆的账号条件；若要求严格冷启动，应另建可恢复的隔离状态，而不是清空日常账号后无法恢复。

## 7. 对评测集、指标和编排的调整

### 7.1 先分能力与条件，再安排 20 个场景

保留既有 20 场景作为首轮诊断规模，但按主动记忆、自动记忆、更新／冲突、经验应用、淘汰／遗忘、隔离边界分组。四端执行范围与有效分母应逐项公开；部分能力未就绪或不适用时，不伪造四端完全相同的有效样本数。

原有示例配置中的统一 `memory_wait_seconds=10` 应改为各端的学习条件／观察窗口：AStudio 检查候选年龄与两阶段完成；WorkBuddy 按每晚整理或明确的主动更新条件；QwenWork 观察工具、文件和维护状态；DoubaoWork 区分主动刷新、自动周期及删除延迟。超时也要区分前置条件未满足和已满足条件后的记忆形成失败。

正式执行前，每端先用少量探测确认“能写入、能在新会话使用、能更新、能清除及验证”。这类前置探测单独编号，不计入 20 场景的能力得分。AStudio 未确认有效启用、任一端未确认作用域／等待条件时，先记录未就绪，不先记作记忆能力零分；通过前置条件后发生的真实 E2E 失败，则保留在预先约定的分母中。

### 7.2 淘汰策略需要独立实验，不能只做清空后提问

| 实验 | 控制与刺激 | 应观察的结果／指标 |
| --- | --- | --- |
| 访问频率 | 等年龄、等重要性的高低频事实；控制重复查询本身带来的重写入 | 分频率组留存率、优先保留差异；无检索日志时只称行为相关性 |
| 时间衰减 | 同类事实设置不同真实存活时长／未访问间隔，固定新增干扰量 | 分时间桶留存率、首次不再可用时间区间；不将检索失败直接解释为物理删除 |
| 容量压力 | 逐步新增可核验条目，设置重要性与新旧对照 | 容量曲线、重要事实保留率、低价值淘汰率、误淘汰率、拒绝写入与覆盖比例 |
| 语义淘汰与合并 | 重复、过时与冲突条目；保留不能丢失的关键信息 | 去重／压缩后的信息保持率、旧值残留率、新值遵循率 |
| 用户主动清理 | 明确忘记指定事实，并混入应保留的对照事实 | 删除请求遵循率、目标残留率、非目标误删率、删除生效延迟 |
| 整个环境重置 | 清除后新会话、恢复所需开关并检查再生成 | 重置成功率、验证耗时、跨轮污染率；属于评测可靠性指标 |

自然时间实验与加速实验分开报告。修改本地时间戳、内部时钟或 TTL 参数会改变实验条件，也未必影响服务端时钟；不能把这种结果当成真实使用下的时间衰减成绩。本次不改系统时钟，也不填满日常账号做容量实验。

### 7.3 将存储、读取与行为分开记录

建议保留四层状态：**写入是否成功、是否进入可检索／可注入集合、是否被实际取用、回答或行动是否正确**。源事实仍在文件中却未注入、检索取回却使用错误、已经被存储淘汰，是不同失效类型。无内部证据时不强行作细粒度根因归因。

记忆形成成功率、跨会话使用正确率、新值遵循率、旧值残留率、重要事实留存率、非目标误删率分别给出分子／分母；延迟注明起止事件和未生效样本。关闭记忆、用户要求遗忘、管理页物理删除和自动淘汰各自报告。问“你还记得旧密码是 ABC 吗”会把答案重新提供给模型，不能用于判断遗忘；应使用不重述目标值的新会话查询。

General E2E 的执行身份绑定、原始轨迹、冻结证据和独立评分仍可复用。需要增加的部分是多会话阶段、各端学习与淘汰条件、重置验收和背景状态记录；正式结论仍是客户端与底层模型组合在指定条件下的表现。

### 7.4 Codex 对照条件应记录到主机、版本与源会话资格

后续若将 Codex 纳入验证，实验配置应补记 `host_id`、有效 home／SQLite 位置、内核版本、`features.memories`、`version`、`dual_write`、生成／使用开关，以及是否允许工具会话参与学习。截图中的 Local 总开关开启，只证明界面状态，不能证明本轮实验已经写入、整理并读回。

无记忆对照要在进入新会话前配置好条件，已有会话的摘要不会因切换按钮而自动从历史上下文消失。关闭工具会话学习的实验应另设组，不将它当作关闭全部记忆。容量与访问频率实验要区分 v1／v2，并固定双写条件；默认空闲门槛和整理冷却要求也意味着不能复用统一 10 秒等待。[C1、C3–C7]
