# AgentCube 沙箱执行阶段接入方案

## 1. 架构决策与交付边界

首期支持 **AStudio 的 General、Web 两类 E2E**，按“本地 POC → 正式执行器 → 现有 Skill 交接”推进。每个任务的每次 run 使用独立沙箱，评分和报告继续由现有客户端 Skill 驱动。

采用独立入口 **`eval/run_e2e.py`**，公共实现放在 **`src/e2e/`**，设计、POC 记录和使用说明放在 **`docs/design/e2e-sandbox/`**。

选择独立入口的原因是，现有 `eval/run_batch.py` 将 CLI Harness、Docker 执行和即时评分耦合在一起，而沙箱 E2E 需要远端 GUI 生命周期、异步观察、产物回收及跨阶段交接。复用其任务解析、筛选语义和来源追踪能力；需要共享的纯逻辑抽取后供两套入口调用，不直接导入并执行旧入口。

实现分为以下边界：

- **任务准备层**：选择题目，冻结任务定义、公开执行材料与私有评分材料。
- **环境层**：AgentCube session、命令、文件传输、健康检查和销毁。
- **产品驱动层**：模型配置、一次发送、原生身份绑定、终态观察、停止与证据导出。
- **场景适配层**：分别生成 General、Web 的现有正式执行产物和评分交接材料。
- **执行服务层**：并发、多 run、持久化状态、恢复、取消及事件输出。

首期只注册可执行的 AStudio 驱动。WorkBuddy、QwenWork、DoubaoWork、Loomy 通过同一驱动接口扩展；没有实现或验证的客户端明确返回“不支持”。

本轮不修改可视化平台，不实现无头评分。保留可供平台调用的 Python 服务接口、结构化事件和结果索引，后续接入平台现有 WildClawBench 命令构造与调度层。

## 2. 阶段一：本地 POC 与进入正式接入的门槛

先复现 BVT 的平台调用顺序，保留原脚本作为对照。POC 使用三文件统计任务和现有模板，可沿用 `preset_model=auto`，但记录实际观测值，不将其作为精确模型评测。

POC 执行以下流程：

1. 读取外部平台配置，通过环境变量取得凭据；创建 session 并立即记录身份。
2. 检查 Linux 数据面、Windows VM 和 wgui，就地读取 CLI 帮助、版本及可用协议说明。
3. 上传公开素材，注入 Prompt 和请求，执行 configure、task run。
4. 本机等待 job，读取运行结果；主动触发 task collect，下载产物和证据。
5. 严格检查 `answer.md` 内容为 `3`，核对实际工作区及素材清单。
6. 从原生轨迹核对本题 Prompt、cwd 和可取得的会话身份；不能仅凭“最新三个 rollout”认定归属。
7. 核验本地产物后请求销毁 session，检查响应并记录最终资源状态。

每次 POC 保存配置摘要、版本、请求及响应、阶段耗时、原始日志、产物、文件清单与 SHA，以及成功或失败的明确原因。失败路径也尝试回收证据。

**进入正式接入的门槛**是：平台链路跑通、答案正确、工作区映射明确、本题轨迹可准确归属、资源清理状态可核验。原脚本 PASS 本身不足以通过该门槛。

POC 同时形成镜像能力清单，核对：

- 唯一运行身份及原生 thread/turn/session/cwd 的获取方式；
- 模型、推理强度的设置和实际值回读；
- 完成、失败、取消和待交互的区分；
- 完整轨迹、最终回复和任务进程收口的导出；
- 正式执行不使用 BVT 固定运行时限的实现方式。

缺失能力整理为维护方升级需求；源码或新镜像提供后继续验收，不通过猜测请求字段、默认成功或伪造证据绕过。

## 3. Python 入口、任务选择与工作目录

入口提供 `poc`、`run`、`resume`、`status`、`cleanup` 子命令；`run --dry-run` 只解析、准备和展示任务计划，不创建沙箱。

主要参数如下：

| 参数组 | 参数与行为 |
| --- | --- |
| 工作目录 | `--workspace-root`：统一存放任务定义、私有评分材料、执行状态、产物和轨迹 |
| 场景与数据集 | `--scenario general\|web\|all`；General 显式指定 `--dataset`，支持已登记冻结数据集 |
| 任务范围 | `--task` 指定定义文件，或重复传入 `--task-id`、`--category`；未缩小范围时执行选定场景/数据集全集 |
| 补充筛选 | `--tag`、`--exclude-tag`、`--modality`；包含标签取并集，排除条件后应用；显式单题不静默被过滤 |
| 被测配置 | `--harness`、`--model`、`--reasoning-effort`；正式执行要求模型明确，显式指定的配置必须能设置并核验 |
| 调度 | `--concurrency`，默认 1，兼容别名 `--parallel`；`--runs`，默认 1 |
| 平台配置 | `--agentcube-config`、`--template`；凭据从环境变量读取，不写入命令行或分发包 |
| 作业身份 | `--job-id` 可指定，否则自动生成；恢复必须使用既有作业身份 |
| 调试与资源 | `--keep-on-failure`，默认关闭；平台 TTL 和单次控制操作超时通过配置文件设置 |

题目从仓库筛选后，调用现有场景准备能力自动生成材料。General 保留所选数据集的 ID、digest 和原始顺序；子集另存选定范围，不冒称完整数据集。历史冻结数据集读取其对应快照。Web 沿用现有 Profile 识别逻辑，详细 Profile 与 ArtifactsBench 分开准备。

工作目录采用以下结构：

```text
<workspace-root>/<job-id>/
  job-config.json
  selection.json
  events.jsonl
  state/
  definitions/                   # 本地任务原文、公开材料、私有评分材料
  runs/run-0001/
    <scenario-and-profile>/
      <harness-unit>/            # 保持现有场景目录约定
        manifest.json
        execution/
        evidence/
        receipts/
        score/
        sandbox/
  runs/run-0002/
  handoff.json
  run-summary.json
```

每个场景/Profile、每次 run 形成独立子批次，保留原 task ID。多 run 是独立重复实验，不当作失败重试，也不覆盖旧 attempt。

只有公开 Prompt、素材和已声明的执行依赖上传沙箱。评分标准、GT、grader、平台凭据及其他任务材料留在本地。

## 4. 执行生命周期、并发与 Skill 兼容

任务生命周期固定为：

**准备 → 创建沙箱 → 健康检查 → 核验能力与配置 → 上传 → 一次发送 → 观察 → 远端收口 → 收集 → 本地冻结 → 交接 → 销毁。**

- 将工作项展开为“任务 × run”，在整个作业范围内统一调度。并发 10 表示至多持有 10 个本作业的沙箱生命周期槽位，不是一个客户端内的 10 个会话。
- 创建中、运行中、回收中及销毁未确认的 session 都占用槽位；确认释放后才补位。
- 本地持久化唯一 attempt、session、job、Prompt SHA、原生身份及关键调用意图。`golden` 不作为正式逻辑身份。
- 创建或派发请求结果不确定时，恢复只核查原操作，不自动重复。平台缺少可靠查询能力时进入待处理状态并停止相关新建操作。
- 普通独立任务失败不取消其他任务；所有失败、未知和未执行项保留在汇总中。控制端中断后可沿原状态恢复。
- General/Web 正式执行不沿用 BVT 的固定做题 deadline。单次 HTTP、健康检查、采集和清理分别限时；平台 TTL 到期记为基础设施问题，不记作模型能力零分。
- 远端原生终态、任务进程收口、工作区快照和下载文件哈希形成证据链。本机目录静默不能替代 Windows 内的收口证明。
- 模型或显式推理强度不匹配、无法核验时，在发送 Prompt 前拒绝；不得静默回退到 `auto`。

General 使用现有执行状态、轨迹、资源和回执契约；Web 使用现有 automation state、execution record、execution receipt 和候选策略。为远端执行增加受版本控制的来源验证适配，区分 Windows cwd 与本地候选路径，避免套用 macOS 本机采集假设。

评分交接继续使用现有准备、编排、评分和报告 Skill。只对必要的来源识别、验证和发行装配增加兼容支持，保持 rubric、权重与评分语义不变。Web 仍遵守现有成功批次准入要求，不删除失败题来伪造完整回执。

`handoff.json` 列出各子批次的评分入口、回执、候选和轨迹摘要、所需 Skill 身份及未就绪原因。结构化事件覆盖任务、run、attempt、session、阶段和错误；退出状态区分完成、失败、参数/能力不支持、需处理及中断，便于未来平台接入。

## 5. 测试、验收与默认约束

按以下顺序验收：

1. **协议与状态测试**：覆盖创建响应丢失、提交后断连、控制端重启、重复恢复、部分下载和销毁失败，证明不重复发送、不覆盖证据、不提前释放槽位。
2. **任务与配置测试**：覆盖单题、分类、场景、冻结数据集、标签、多 run、配置漂移，以及私有评分材料不进入上传清单。
3. **证据测试**：拒绝串题轨迹、错误 cwd、候选哈希漂移和缺少远端收口证据；未知资源指标保持 null。
4. **真实单题验收**：POC 通过后，各执行一题 General 和 Web，并由现有 Skill 完成评分、报告，验证完整交接链。
5. **并发与多 run 验收**：先验证 2 路隔离和恢复，再验证 10 路短任务；保存实际 session 和原生执行区间证据。未经真机验证的并发规模明确标为未验收。
6. **回归检查**：运行受影响的 CLI 筛选、General/Web 契约、工作区准备和 Skill 打包测试，确认旧本地执行入口仍可用。

默认一次调用评测一个 Harness 和模型配置；首期仅 AStudio 可执行。其他客户端、可视化平台 UI、无头评分智能体及跨 run 分数聚合均留待后续阶段。

当前尚未启动 POC。实施后的第一个交付物是带原始证据的 POC 结论及镜像能力清单，只有满足门槛才进入正式执行器接入。
