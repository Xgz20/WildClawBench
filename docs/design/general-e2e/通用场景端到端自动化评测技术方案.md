## 1. 已确认决策与首版范围

1. 初期使用 `tasks/extension` 中标签包含 `custom`、排除 `ppt`、`web-site`、`web-site-gen`、`invalid` 的 60 题，冻结为 `general-custom60-v1`；后续扩题发布新数据集版本。
2. 新建 `eval_general_e2e/` 承载仓库集成入口和适配；保留现有 `eval_e2e/` 的旧入口及结果读取能力。
3. Skill 源码按 `tools/report/skills/general-e2e/` 和 `tools/report/skills/web-e2e/` 分类；其他分析、校验和报告 Skill 不强行归入这两个场景。
4. 对外提供独立 Skill ZIP、执行数据包和私有评分数据包。公共代码单一来源维护，构建时装入所需 Skill；执行、评分、报告均不依赖 WildClawBench checkout。
5. 保留分阶段调用，提供 `run-general-e2e` 串联一条 Prompt 全流程、恢复和离线交接；支持人工参与的执行模式。
6. 语义评分默认使用固定 Codex 模型和推理强度的独立评分会话；API Judge 是显式可选后端，失败时不得静默切换。
7. 原任务自动规则、rubric、分值锚点、权重和题意保持不变。语义裁判协议单独版本化，不宣称新旧裁判结果天然等价。
8. 逐题统计输入、输出、缓存 Token、模型请求、工具调用和耗时，报告展示总量、已知小计与覆盖率；执行、裁判、控制三类消耗分账。
9. 首版先完成 AstronStudio macOS 单题和小批闭环，再推进 Windows。WorkBuddy、QwenWork 和 DoubaoWork 半自动接入安排在 AstronStudio 双平台基础之后。

首版交付包括 AstronStudio 双平台全流程、两种语义裁判、7 个独立 Skill、60 题版本化数据包、报告和可恢复状态。完全离线安装、所有桌面客户端一次性适配、重写题目以及替换现有 Web 评分协议均不作为首版必需条件。

当前 API Judge 的轨迹默认预算为 80,000 字符；`build_judge_evidence()` 保留首条用户消息与最终回复，再从后向前补充事件，并记录遗漏和截断。Workspace 默认总预算 80,000 字符，普通文件默认单文件 12,000 字符。这些策略比简单截尾保留更多信息，但语义 Judge 仍无法按需回查遗漏内容。评分智能体的改进点是可追溯地补充证据，准确性提升需另做校准。

已有 Web 真机证据只说明相应 Web 版本组合的能力；本方案不能据此标记 General E2E 已验收。历史聚焦测试也不能作为本次新接口或新发行包的测试结果。

以下首版目录和模块名称已由 `GENERAL-E2E-ADR-0001` 锁定；目录内容仍按计划逐项实现：

规则 core 的抽取采用渐进兼容：旧 `src/utils/grading.py` 保持函数签名和默认 API Judge 路由，通过适配层复用同源实现；新系统通过正式 core 接口调用。需要一并审计 `judge_audit`、`workspace_evidence`、transcript loader、依赖文件和动态复制资源，不能凭几个顶层 import 判断包已经自包含。

通用 Driver core 只关心客户端、任务目录、Prompt、会话身份、终态和原生采集；Web/General adapter 各自定义 manifest、产物选择、回执、评分准入和报告语义。Web 的 `.git` 禁止项、`node_modules` 过滤以及“整批成功才评分”等规则不能直接用于通用任务。

G1-03 已建立三个 `1.0.0` canonical 组件：`desktop-runtime` 提供确定性进程调用与文件类型探测，`resource-metrics` 提供 Profile 驱动的原生指标解析和受限轨迹读取，`workspace-integrity` 提供显式策略驱动的目录树哈希、冻结文件读取和漂移校验。AstronStudio General source adapter 只绑定 `tools/report/e2e-shared/`，不引用 Web Skill。G2-03 已生成正式 General transcript；G2-04 再将冻结 provider events 映射为正式 `resource-metrics-v1`，不把 G1-03 的内部 native observation 直接当成协议产物。Web adapter 继续固定原 schema、Qwen Profile、`.git`/运行时目录策略和受管评分 marker，源码版本为 execute `1.12.7`、orchestrate `0.2.7`、score `4.5.3`。

G1-04 已实现统一构建器和 13 个 Skill 的装配计划。构建时跳过 Web 源码中的过渡快照，从 canonical 组件重新 vendoring；每个 ZIP 都生成 `bundled-components.json`，并在发布清单记录 Skill 内容 SHA-256 与 ZIP SHA-256。构建器校验运行时相对 import 闭包、源码和归档链接、归档路径、checkout 绝对路径及组件内容，验包时再次核对清单和哈希。ZIP 使用固定时间戳、固定文件顺序、固定 POSIX 权限和 `ZIP_STORED`，相关源码由 `.gitattributes` 固定为 LF，以消除文件权限、zlib 版本和换行策略造成的跨平台字节漂移。以上结论来自 macOS 开发机静态/模拟回归，不替代 Web 新版本或 General 的真机准入。

目录迁移保持 Skill 名称、调用方式和 ZIP 顶层目录不变。同步调整打包器、测试、文档及仓库 `.agents/skills` 链接；本机安装链接通过明确的安装/迁移入口更新。先迁目录并通过已有 Web 回归，再按组件抽取公共实现；避免同一次变更同时改目录、Driver 行为和评分语义。

## 4. Skill、阶段和运行方式

| Skill | 输入 | 输出与责任 |
| --- | --- | --- |
| `prepare-general-e2e-workspaces` | 版本化 dataset bundle、Harness 配置、输出位置 | 批次 manifest、execution/scoring ZIP、报告配置、所需 Skill 清单 |
| `execute-general-e2e` | execution 包、执行策略 | 自动 Driver 或人工操作清单、原生 session 绑定、执行终态和初步资源记录 |
| `collect-general-e2e` | 执行状态、原生轨迹、终态 Workspace | 冻结候选、原始和标准化轨迹、指标、证据清单、正式执行回执 |
| `orchestrate-general-e2e` | 有效执行回执、scoring 包、裁判配置 | 独立评分工作空间、评分队列、Codex 任务或 API Worker、有效 submission |
| `score-general-e2e` | 单题评分工作空间、冻结裁判配置 | 自动规则分、语义分、证据引用、评分审计、标准 `score.json` |
| `report-general-e2e` | 校验通过的回传包及报告配置 | 可复算 JSON、Markdown、Excel，附范围、协议和异常分母 |
| `run-general-e2e` | 用户明确选择的阶段与配置 | 串联上述能力，维护阶段状态，完成 package/import 和恢复 |

G1-02 已实现上述七个 Skill 的 canonical 目录、`skill-metadata.json`、`agents/openai.yaml` 和 `.agents/skills` 发现链接。`python -m eval_general_e2e skills --json` 提供机器可读注册表，`python -m eval_general_e2e check-layout` 校验七个入口、共享组件绑定和旧 `eval_e2e` 文件。G2-06 后，prepare 为 `0.2.0/operational`；execute 为 `0.4.0/operational`，支持 AstronStudio macOS 只读 probe、单题 Prompt 一次发送、原生身份绑定、可信终态、单槽队列和同 attempt 恢复；collect 为 `0.4.0/operational`，支持轨迹与资源归档、精确任务进程收口、exact-all 候选冻结、不可变复核和正式执行回执；其余四个仍为 `0.1.0/interface_only`。所有尚未 operational 的完整业务阶段都必须停止，不能回退到 Web 或旧 `eval_e2e` 链路。

阶段命名区分 `collect-evidence`（采集单元执行证据）与 `import-return`（管理员导入回传），避免两种 collect 含义混淆。组合器只执行所选阶段，恢复沿用冻结配置；单阶段也必须遵守同一输入、回执和哈希契约。

自动主链路：prepare → execute → collect-evidence → score → package → import-return → report。`score` 内部由 orchestrate 分发单题评分，不能让单题评分 Agent 调度下一题。

人工协作沿用同一包格式：execute 进入 `NEEDS_HUMAN`，人工完成选目录、选模型、粘贴唯一 Prompt、导出轨迹等机械动作，再由 collect 校验收口。记录 `execution_mode=human_assisted`、操作事件和语义干预次数；人工补充答案、修改候选或发送指导性后续消息必须单独标记，不与无干预运行混算。没有轨迹时，最终文件只能支持部分检查，不能补造工具记录或 Token。

未来单 Prompt 示例（目前不可执行）：

```text
使用 $run-general-e2e，在 AstronStudio macOS 完成已提供的
general-custom60-v1 execution/scoring 包的执行、证据采集、评分和回传。
语义评分使用 codex-agent-judge-v1，模型和推理强度使用本批已冻结的配置。
首次执行并发 1；遇到需要人工输入的状态保留现场；从状态文件恢复。
```

被测模型配置和裁判配置分别记录。被测客户端可显式选模型或保持当前模型并回读；推理强度只有具备可靠回读时才声明 verified。评分模型和推理强度必须在首次语义评分前指定并冻结，不静默沿用可能变化的客户端默认值。

## 5. 数据集与独立分发

### 5.1 冻结任务版本

`general-custom60-v1` manifest 至少包含：完整有序 task IDs、唯一性校验、筛选条件、任务 Markdown SHA、Prompt SHA、exec 素材清单与 SHA、私有评分材料 SHA、source revision、超时、grading 类型、rubric/权重和依赖声明。

逐题能力矩阵和可复核 JSON 由 `eval_general_e2e.datasets.capability_audit` 确定性生成。生成前必须确认当前任务、Workspace 与 manifest lock 完全一致；grader 只用 AST 检查，不导入或执行。矩阵区分“代码里出现 transcript/tool parser”“`grade()` 接口接收”和“可达路径实际读取”，并记录执行/评分素材、结果路径、运行时/工具能力、外部评分依赖、全量轨迹字段及 Windows 风险处置。

动态标签筛选仅用于首次选题或显式创建新版本。运行、恢复和报告以 manifest 的精确集合为准；60 题规模变化、任务文本或评分材料变化均需新版本或新的可辨识 digest。纯回复任务也必须保留最终助手回复，不能用“有无生成文件”判断完成。

Prompt 只允许确定性路径映射，并记录原文哈希、映射及发送文本哈希。Windows 的 `python3`、Shell、路径分隔符等差异优先通过运行环境解决；必须改命令或题意时发布可辨识变体，不能悄悄改题并保持相同版本。

### 5.2 分发材料

| 材料 | 内容 | 可见范围 |
| --- | --- | --- |
| dataset bundle | manifest、任务定义、exec 与私有评分素材，按权限分层 | 管理员 prepare 输入；独立准备无需克隆仓库 |
| `__execution.zip` | 单题 Prompt、初始 workspace、最小 manifest、工具与人工清单 | 被评 Harness 只选择单题执行目录 |
| `__scoring.zip` | automated checks、rubric、GT/fixtures、权重、契约哈希 | 执行终态后合入独立评分目录 |
| 单 Skill ZIP | SKILL.md、脚本、引用文档、所需 vendored runtime、依赖锁和组件清单 | 按阶段独立安装 |
| suite ZIP | 七个独立 Skill ZIP、skills-manifest、安装说明 | 便于批量交付，不改变单 Skill 独立性 |
| return ZIP + receipt | 候选、轨迹、资源、评分结果与证据清单 | 管理员导入、复核和报告 |

G1-05 已实现独立 prepare：`tools/e2e-build/build_general_release.py` 生成七个 General Skill ZIP、三份 schema、release catalog、安装说明和 suite ZIP；catalog 显式记录每个 Skill 的版本、阶段、实现状态、组件、内容 SHA、ZIP SHA 和 source revision。suite 只是七个独立 ZIP 的确定性集合，不改变单 Skill 独立性。

已安装 `prepare-general-e2e-workspaces` 从外部 dataset bundle、suite ZIP、配置 JSON 和输出位置准备批次，不读取 WildClawBench checkout。它携带 `dataset-bundle-verifier 1.0.1`，先验证 dataset、catalog、嵌套 Skill ZIP 和全部哈希，再按 dataset manifest 顺序生成每个 unit 的 `__execution.zip` 与 `__scoring.zip`。execution 包只包含映射后的 Prompt、初始 Workspace 和最小运行清单；scoring 包只包含任务原文、评分 contract 和 GT。`/tmp_workspace` 确定性映射为 `./workspace`，manifest 同时记录原始、来源和发送文本 SHA。受限 symlink 作为 ZIP 元数据复制，不在宿主文件系统解引用；绝对、反斜杠或归一化后越界的链接目标被拒绝。

批次根目录保留 `manifest.json`、`report-config.json`、`release-catalog.json`、七个锁定 Skill ZIP 以及每个 unit 的双包。批次、release、dataset、Skill 与输出 archive SHA 均被冻结；未知协议、乱序/未分配任务、重复或越界成员、符号链接类型漂移、哈希篡改和额外文件失败关闭。仓库外 fixture 已从构建后的 prepare Skill ZIP 运行，且清空 `PYTHONPATH` 后仍只依赖 vendored dataset verifier 和 Python 标准库。

### 5.3 共享源码的装配

发布流程：场景 Skill 源码 → 临时 staging → 装入所需共享组件与评分/报告 core → 生成 `bundled-components.json` → 校验依赖闭包 → 内容哈希 → ZIP 哈希 → 发布清单。

每个组件记录 name、version、source revision、content SHA；Skill 内容哈希必须覆盖 vendored 内容。Web 和 General 可以携带不同、已验收的组件版本，升级一个 Skill 不改变另一 Skill 的已安装文件。运行时不引用兄弟 Skill 内部模块、不依赖仓库绝对路径或源码符号链接；组合器可发现并调用已安装阶段 Skill 的正式入口。

G1-04 的实现入口为 `tools/e2e-build/build_skill_packages.py`，构建计划为 `tools/e2e-build/skill-bundles.json`。`build` 从 canonical 源装配临时目录，排除仅用于源码回归的 `test/tests` 和 `node_modules`，再生成 13 个单 Skill ZIP 与 `skills-build-manifest.json`；`verify` 安全解压并复核顶层目录、组件、文件数、依赖闭包和两级哈希。源码测试不会进入发行包，因此仓库内跨 Skill 联调测试不能成为运行依赖。所有发布文件使用固定 LF、时间戳、顺序、存储方式和权限；组件内容哈希覆盖相对路径与文件字节，Skill 内容哈希还覆盖 `bundled-components.json` 和 vendored 文件。

Web `prepare-web-e2e-workspaces` 仍保留一个管理员开发入口：从显式 `repo_root` 读取 Web 任务和五个阶段 Skill 源码。该仓库相对引用必须同时出现在构建计划、包内清单和验证结果中，不能由构建器代码静默豁免；其他 Skill 不允许登记此例外。General prepare 已改用 dataset bundle 与 release catalog；这不改变 Web prepare 的既有行为，也不把尚未实现的六个 General 阶段 Skill 提前记为 operational。

“独立分发”指不依赖 checkout，并不自动意味着无 Node/Python/Docker 或无网络。依赖使用锁文件安装到 Skill 专属环境或受管缓存；评分 core 的 wheel 若有第三方依赖，应包含完整锁定清单。完全离线模式另外分发对应平台 wheelhouse、Node 依赖及 Docker 镜像，普通发行包不能冒称完全离线。报告还必须明确 XLSX 引擎和安装依赖，不能依赖控制客户端碰巧预装的库。

## 6. 执行、轨迹与恢复契约

### 6.1 身份和状态

一次执行至少由 `batch_id / unit_id / task_id / attempt_id` 唯一标识。unit 包含 Harness、模型、配置和平台；原生 thread、turn、session、cwd 绑定到该 attempt，不能依赖标题、最近修改时间或文件夹 basename 猜测。

阶段状态采用 `NOT_SELECTED / PENDING / RUNNING / NEEDS_HUMAN / NEEDS_ATTENTION / COMPLETED / FAILED`。执行业务终态另外记录 `completed / candidate_error / timeout / infrastructure_error / cancelled`，与采集完整性、可评分性独立。

发送前持久化发送意图和 Prompt 哈希，发送后立即保存可靠会话身份。发送临界点不明确时先核查原生会话；无法唯一确认就停在 `NEEDS_ATTENTION`。恢复继续原 attempt、thread 和 deadline，不重发已确认提交的 Prompt。评分恢复也复用原评分 thread 与 cursor；原任务未确认终态，不创建替代任务。

G2-02 已实现 AstronStudio macOS 单题状态机。执行器只消费已验证的 execution unit 和 G2-01 冻结配置；发送前重新回读客户端版本、CDP 主进程、模型、推理强度、权限及活动会话。新任务、Workspace、Prompt 内容和发送动作均要求唯一匹配，先落盘 `intent_persisted` 和 `dispatch_attempt_count=1`，再执行一次发送。发送后以 route thread、相对发送前基线发生变化的 turn、provider session 和绝对 cwd 四项共同绑定身份，不用任务标题、最近线程或文件变更猜测归属。

原生 `projection_turns.state=completed` 是成功终态，不要求 Workspace 发生变化。S1 文件任务与 S4 纯回复任务均在 AStudio 3.3.1、GLM-5.2、High、完全访问下真实完成，Prompt 发送计数均为 1；S1 的已完成恢复前后三个证据文件 SHA 不变，S4 在状态库热写快照失败后恢复同一 attempt 并收口，未重发。展开侧栏时全局“新建任务”与逐项目“新建对话”分开选择；热写快照失败在副本级退避并在终态轮询级继续恢复。证据见 [G2-02 验收索引](evidence/g2-02/README.md)。G2-05 已将两题既有执行状态、G2-03 轨迹和 G2-04 资源证据重新绑定后生成 `complete / stable` 的正式 execution record 和 collect receipt；旧 G2-02 临时回执仍只作为执行阶段历史证据，不用于评分准入。

G2-06 在单题状态机外增加持久化有序队列。queue digest 冻结 batch/unit、dataset、manifest SHA、运行配置 digest、任务顺序、`ui_slots=1 / run_slots=1`、失败继续策略和 Driver 参数；恢复参数漂移即拒绝。队列第一次读取任务状态时显式登记唯一 `selected_attempt_id`，后续发现不同 attempt 报 `ATTEMPT_SWITCH_REQUIRES_NEW_QUEUE`，不按最新目录或时间隐式选择。当前题为 `RUNNING / NEEDS_ATTENTION` 或缺少可恢复状态时，下一题保持 `PENDING`；只有 completed，或显式继续策略下的可信 failed 终态，才允许切题。单题入口新增 unit 级 UI 锁，阻止绕过队列并发操作桌面。

真机四个固定 smoke 在同一单槽队列按 manifest 顺序完成，每题发送计数均为 1。S4 发送并绑定后硬中断 Worker，恢复进程识别死亡 PID 和陈旧锁，以原 attempt/thread/turn/session/deadline 收口后再切题。独立 S3 在绑定后重启 AStudio，原生状态明确为 `interrupted`，队列按原 attempt 保存 `cancelled / ASTRONSTUDIO_TURN_INTERRUPTED`，没有重发或替代任务；重启后 probe PASS 且活动会话为 0。证据见 [G2-06 验收索引](evidence/g2-06/README.md)。`run_slots=3` 仍由代码失败关闭，五题动态补位和并发隔离必须在 MAC-08/G4-05 另验。

### 6.2 轨迹归档和标准化

保存原始可取得的事件、标准化 transcript、事件索引及 adapter 版本。标准事件覆盖 user/assistant 最终回复、工具调用参数和结果、调用关联 ID、错误、时间顺序、可取得的 usage；不要求获取客户端未提供的内部推理内容。

标准化不得把评分会话或后台无关事件混入被测轨迹。路径映射同时保存原始值和规范化值；同一调用的调用/返回不能合并为两次工具调用。验收必须拿真实 AstronStudio 样本验证工具名、参数字段和 `transcript_loader`/原任务规则的兼容性，不能仅确认 JSON 能解析。

提供按事件范围、call ID、文件路径及文本检索的只读证据接口，返回总命中数、分页状态和可回溯定位。完整性有独立字段；未归档原始事件时，索引或摘要不能被描述为完整轨迹。归档应只包含本题关联数据，敏感真实凭据脱敏并保留脱敏范围说明；若影响某检查项，明确不可判定，不伪造原文。

G2-03 已将该契约落到 `collect-general-e2e` 的 AstronStudio 轨迹子能力。归档器对 SQLite/WAL 做只读快照，仅查询执行状态绑定的 `thread_id + turn_id`，并二次校验 provider session、lifecycle generation 和项目 cwd。`commandExecution / fileChange / mcpToolCall` 分别映射为 `command / file_change / 原生 MCP 工具名`，call/result 用同一 ID 关联；路径保留本机原值与 `/tmp_workspace` 规范值。查询器在验证 size/SHA/event count 后提供范围、call ID、路径、文本和分页定位。S1 真机归档 148 个原生事件、24 个标准事件和 5 组调用，S4 归档 319 个原生事件、5 个标准事件及最终回复；两者均为 `complete / omitted=0 / missing=[]`。证据见 [G2-03 验收索引](evidence/g2-03/README.md)。G2-04 补齐资源契约映射，G2-05 再把轨迹、资源和冻结候选封装为正式可复核回执；collect Skill 已整体升级为 `0.4.0/operational`。

### 6.3 收口和评分准入

collect 只有在明确终态、相关进程按本题身份收口、Workspace 稳定且身份匹配后才冻结候选。冻结前后记录快照；冻结后漂移必须报错，不能修改产物以通过哈希。

通用产物策略按任务契约确定：需要 Git 仓库、二进制或缓存作为证据的任务，不可套用 Web 的目录删除规则。清单记录实际包含、忽略和排除内容及其原因；执行原件不因分发过滤而被清理。必要评测材料被排除时阻止完整评分。

可信 timeout/candidate_error 也可以保存部分产物和完整轨迹，按冻结规则评分，保留执行状态。这与现有 Web 成功批次准入不同。基础设施错误、缺失必要轨迹或无法确认终态时，只能输出明确的评测异常及可保留的部分检查结果，不能冒充候选能力为零。

G2-05 已实现上述收口：macOS 使用 Workspace 绝对路径或 cwd 作为精确进程 seed，并包含其后代；发送信号前用 PID、启动时间和命令 SHA 防止 PID 复用，先 `SIGTERM`，必要时再 `SIGKILL`，并要求完整零残留安静窗口。随后以静默前、静默后、复制后源 Workspace 三次 SHA 及冻结副本 SHA 做一致性校验。默认 exact-all 保留所有目录，不继承 Web 过滤；目录例外只能由带理由的显式策略声明，绝对或越界 symlink 失败关闭。evidence 和 receipt 不可覆盖，`--verify-only` 同时重算冻结候选、原始 Workspace、证据清单与正式回执。S1/S4 均取得 `complete / stable / completed` 正式回执，见 [G2-05 证据](evidence/g2-05/README.md)。G2-06 又把每个 execution unit 限定为一个显式队列选择的 attempt；需要重做时重新准备独立 unit 和 queue，collect 不负责从多个 attempt 中猜选。

评分容器、锁、日志和临时目录必须按 batch/unit/task/attempt 唯一命名；保留逻辑 task ID 到运行时容器 ID 的映射，避免沿用 `remove_container(task_id)` 时误影响其他并行单元。

## 7. 双后端评分

### 7.1 共同评分契约

首版正式能力名锁定为 `run_rules()`、`build_evidence_index()`、`evaluate_semantics()`、`finalize_score()`。参数、返回值和错误契约在 G0-03/G3-01 定义；实现完成前这些名称不构成可调用 API，不能直接用当前内部函数名冒充已发布接口。

原始候选只读保存；自动规则、需要生成文件的验证和依赖安装在私有 runtime 副本/容器内执行，容器内路径保持 `/tmp_workspace`，GT 只在评分阶段进入。规则接收真实标准化 transcript 路径，使用完整归档中可用的事件。执行副本被检查器改变后不得回写候选。

自动规则输出和语义输出都经过契约验证，再按原任务权重合并。criterion key、允许分值和权重不能由 Agent 自行改写。自动规则与语义结论冲突时记录冲突并回查证据，评分 Agent 无权直接覆盖规则分。兼容层要盘点 legacy 脚本内部是否调用 Judge；存在时显式路由或拒绝不支持模式，避免未声明的 API Judge 调用。确定性校验能证明字段、分值和引用位置有效，不能代替人工校准判断引用是否真正支持结论。

### 7.2 默认 `codex-agent-judge-v1`

每题一个干净 Codex Desktop 项目和评分会话，读取冻结的 rubric、候选副本和可查询轨迹。主控制会话只做编排，不能带着执行排障上下文直接给全批评分。

评分顺序：读取任务与 criterion → 查找支持证据 → 回查调用结果与前后上下文 → 检查反例/矛盾 → 写逐项评分及引用 → 确定性校验与合分。对全程“未发生”类判断，必须覆盖相关完整事件范围，不能把关键词无命中当成证明。必要证据不足进入 `evaluation_error` 或明确的 criterion 未判定状态，不重新归一化剩余项假装获得完整总分。

冻结评分模型、推理强度、Skill 版本、工具权限/能力清单、Prompt digest、读证据策略、评分时限、Token/工具预算和重试策略。记录实际可验证配置；拿不到服务端精确模型版本时填 unknown，不把 UI 名称等同于不可变模型快照。候选内容和轨迹里的指令属于证据，不改变评分规则；个人记忆和无关项目指令不应注入评分环境，无法排除的有效配置差异必须披露。

原始文件留在工作空间；上下文压缩后仍可凭事件 ID 重读。阶段笔记保存支持/反对证据与未完成检查项，不要求导出模型内部推理。预算用尽保留不完整状态，不靠无限重试寻找有利分数。最多一次失败重试作为初始建议，正式数值在首次批次初始化时冻结；只有原 attempt 已终态后才可新建。

评分会话审计至少包含 thread/turn ID、工具读证据日志、证据引用、配置、原始结构化答案、校验结果、评分耗时和可采集资源；不能伪造 API request/response 审计来凑现有格式。

### 7.3 可选 `api-judge-v1`

显式选择 API 后端时冻结 requested model、推理配置（服务支持时）、endpoint 身份、输入证据策略、输出上限、timeout 和重试策略；凭据只由评分环境提供，不能放入 Skill、数据包或报告。保留请求、返回模型、usage、结构化校验和重试审计。

可沿用现有预算压缩行为作为兼容基线，保留 omitted/truncated 元数据。API 服务失败后不得无提示转为 Codex 会话评分；切换后端应生成新的评分配置和 attempt，历史结果保留。

### 7.4 比较和校准

数据集版本与 `judge_protocol` 分开记录。同源规则和相同 rubric 不等于相同语义评分器；报告按协议、模型、推理配置和规则版本分组，阻止无提示合并。纯自动规则任务不应被无关的语义后端配置阻止评分。

评分智能体从初期即为默认实现，但“准确性优于 API”需实验支持。使用同一批冻结候选/轨迹，做现有 API、改进证据输入的单轮 API、评分智能体三组盲审；优先保持裁判模型相同，做不到时标记模型与协议的组合对照。选 12–18 个具有长短轨迹、前中后关键事件和矛盾证据的样本，关键子集重复评分；人工逐 criterion 复核，并记录误判/漏判、证据引用正确性、重复波动、耗时和成本。正式发布前审核结论，不能以平均得分升高证明更准确。

## 8. 工作空间与结果契约

拟定单元包布局：

```text
<unit-root>/
  manifest.json
  execution/tasks/<task-id>/
    PROMPT.md
    workspace/
  evidence/tasks/<task-id>/<attempt-id>/
    execution_record.json
    raw-trace/
    transcript.jsonl
    trace-index.json
    resource-metrics.json
  receipts/execution-receipt.json
  score/tasks/<task-id>/
    workspace/                    # 冻结候选的评分副本
    private-scoring/              # contract、轨迹、GT、证据、审计、评分结果
  .general-e2e/                   # 本机状态、锁、journal，不给被评 Harness
  submission.json
```

execution 与评分目录分开只是文件分发边界；执行用户/客户端不应有实际访问私有评分材料的权限。正式收集和评分副本带 manifest 与哈希映射，不依赖被评 Agent 自报完成。

每题结果至少包含逻辑身份、来源哈希、执行状态、证据完整性、规则分、语义分、总分/有效性、裁判协议与身份、attempt、资源来源状态以及异常。结果格式可适配到 CLI 的 `score.json / usage.json / task_output / execution_status` 等产物，但不能用文件名兼容代替语义兼容。`submission.json` 枚举冻结任务全集，包括失败/未评题的显式状态，不能因失败而缩小分母。

ZIP 导入校验哈希、唯一身份、相对路径、链接类型及版本兼容性，通过后原子发布。相同回传幂等，内容冲突保留两个 attempt 并要求显式选择；不能覆盖旧证据。评分重跑复用冻结候选，新建评分 attempt，不重新执行被评 Harness。

## 9. 资源口径与报告

复用 Web 的来源状态 `observed / inferred / partial / masked / unverified / unavailable`。每字段独立判定，不因某个 Token 字段不可用而抹去有效工具次数。新增标准字段优先沿用已有命名：

| 分组 | 字段或含义 |
| --- | --- |
| 执行 usage | input_tokens、output_tokens、total_tokens、cache_read_input_tokens、cache_creation_input_tokens、reasoning_output_tokens |
| 请求/工具 | request_count、request_attempt_count、tools.call_count；成功/失败需原生结果支持 |
| 执行时间 | duration_seconds（流程壁钟）、agent_duration_seconds（原生或有依据推导） |
| 来源 | 采集器版本、原生来源哈希、状态、依据、已知小计、排除范围 |
| 其他成本 | judge_usage、control_usage，缺失保留 null，不进入被测执行消耗 |

输入含缓存读取、推理输出属于输出子集时不得重复相加，具体由 provider 已验证口径确认。请求数注明是原生请求、持久化响应还是推导事件，不冒称统一 HTTP 次数。

G2-04 已从 G2-03 冻结的 `provider_runtime_events` 映射标准 `resource-metrics-v1`。Token 按每次 usage 的原生 `last*` 增量求和，并用累计 `total*` 逐步对账；首个累计值减首个增量得到既往 thread 基线，因此不把前轮用量计入本题。`request_count` 是已对账 usage 推进次数，固定标记 `inferred`；不可见 HTTP 尝试和 cache creation 保持 `null/unavailable`。工具调用按唯一 `item.started` call ID 与 trace index 集合复核，result 不重复计数。流程耗时来自 Driver attempt，Agent 耗时来自绑定 turn 的 start/completed 原生时间。每字段另有 coverage、metric source 和仅限部分数据的 known subtotal。S1/S4 真实对账见 [G2-04 证据](evidence/g2-04/README.md)；G2-05 已将这些资源文件纳入正式 evidence manifest 和 collect receipt。

报告总览展示任务总数、有效评分数、执行完成/超时/错误、评测异常、六类和难度结果，以及输入/输出/缓存/请求/工具/耗时。仅全集字段有效覆盖时展示完整总量，否则展示已知小计和覆盖数/分母；全缺失不补零。并行任务耗时之和与批次壁钟分别展示。

候选已确认失败且可评分时按任务规则计分；评测系统失败不解释成能力零分。能力对比使用共同有效任务并披露分母；若需要兼容旧 CLI 包含异常零值的总览，另列并明确名称，不能与有效样本均分混淆。评分协议不同或缺失范围不同的结果不自动合并排名。

JSON 是可复算数据源；Markdown 与 Excel 从同一聚合结果生成并核对。初始建议工作表为“总览”“分类与难度”“用例明细”“资源覆盖与异常”，必要时增加裁判成本表。导出实现须能在仓库外安装运行，实体/定价/显示配置随包或显式报告配置提供；不能运行时读取仓库 `entities.yaml`。

## 10. AstronStudio 平台顺序

执行及评分并发初期均为 1；单题、串行切题和恢复通过后再验证 3 槽。执行 UI 始终单槽；每个后台 attempt、评分会话及容器独立，不能直接继承 Web 的默认并发验收结论。

### 10.1 macOS 优先

- 通过实际安装路径和版本探测 AstronStudio，复用本机 CDP 与项目路径回读；发送后绑定 thread/turn/session/cwd。
- G2-01 已冻结首台真机配置：macOS `26.6.2/x86_64`、AStudio `3.3.1`、loopback CDP `9240`、状态库只读 WAL 快照、UI 模型 `GLM-5.2`、推理 `High`、权限“完全访问”，初始执行并发 1。探针精确选择 `title=AStudio` 且路径为 `/index.html` 的主页面，不能误选同一进程的 `Voice HUD`；[探针证据](evidence/g2-01/astronstudio-macos-probe-2026-09-17.json)和[冻结配置](evidence/g2-01/astronstudio-macos-run-config-2026-09-17.json)只证明 G2-01，不证明项目选择、Prompt 发送或用例闭环。
- 在四个 smoke 上同时验证原生轨迹、标准化轨迹、自动规则和两种语义评分；再推进小批、恢复、报告和仓库外发行包。
- 原 Web AstronStudio 实现在 macOS 的任务进程枚举/终止能力存在缺口，General 正式终态冻结前需补齐或证明相应任务无残留；`supported=false` 不能视为清理验收通过。
- 记录 Node/Python/Docker 与评分镜像架构。Apple Silicon 与 Intel 的 Docker 平台/依赖差异单独验收，不把一个架构的通过外推到另一个。

### 10.2 Windows 紧随

- 动态发现客户端安装位置和状态库，不硬编码用户名；保留只读 SQLite 有界快照/锁等待，验证 UTF-8、中文/空格路径、CRLF 和日志编码。
- 使用原生 `.cmd`/PowerShell 入口，Python 优先可用的 `py -3` 或 `python`；验证任务要求的 Shell、`python3` 与实际运行环境对应，不能因环境缺失给模型扣分。
- 初期采用短工作目录，例如 `D:\g-e2e\w\<short-id>`；发送前验证依赖工具的路径限制，包内保留完整 task ID。本机根路径与逻辑身份分离，跨机映射不能仅比较路径尾部。
- 按完整可执行路径核验进程和 CDP，隔离控制进程注入的 `CODEX_*`、`CHATGPT_*`、Node IPC 变量；精确终止本题相关进程并确认静默后冻结。
- 验证 Codex Desktop 项目注册、固定评分配置、原评分任务恢复；人工启动或跨机评分可作为阶段能力，不能代替 Windows 本机完整闭环验收。
- 自动规则的统一基线为 Linux 评分镜像。Windows 本机评分需验证 Docker Desktop/WSL2 后端、磁盘挂载与镜像；未就绪时允许 Windows 执行→macOS 评分并明确标注跨机路径。

Windows 首次接手必须先查看配套计划的当前状态和平台矩阵，记录 OS/架构、客户端/Codex 版本、源码 revision、Skill/组件/镜像 digest、dataset digest；配置变化按受影响范围重跑验证。

## 11. 推进顺序、风险与审核边界

建议顺序：契约和可分发骨架 → AstronStudio macOS 四题完整闭环 → macOS 小批、恢复与 API 后端 → Windows 探针、四题和跨机交接 → Windows 本机评分与恢复 → 双平台 60 题、裁判校准及发行验收 → 其他 Harness。

| 风险 | 应对与验收 |
| --- | --- |
| 抽取共享代码影响 Web | 先迁目录、后抽组件；Web 原测试与受影响真机 smoke 单独记证据 |
| 轨迹标准化丢失语义 | 原始事件可回查；自动规则 fixture 和真实样本逐项比对；缺证据不猜 |
| Agent 评分波动或漏检 | 固定配置、按 criterion 取证、完整性检查、盲审与重复校准 |
| Windows 依赖或路径失败 | 发送前环境检查；跨机交接与本机闭环分列验收 |
| API 与 Agent 分数被混算 | 冻结 judge protocol；按协议分组，必要时同一候选重评 |
| 无仓库运行仍隐式读取源码 | 仓库外解压、非仓库 cwd、移除 PYTHONPATH 与路径依赖扫描、端到端 smoke |
| 中断后重复发送或覆盖 | attempt/journal/回执，未知终态暂停，恢复核对原会话 |

审核时重点确认：状态与异常分母、语义评分协议、跨机和本机边界、共享代码装配及任务产物过滤。评分模型/推理强度具体取值、目标客户端版本、镜像 digest 和预算数值留到首次实施预检时记录；这些是运行配置待定项，不阻止先实现接口和文档评审。
