## 1. 决策结论

1. General E2E 使用独立的 `eval_general_e2e/`、General Skill 源目录和版本化契约，不在原 `eval_e2e/` 内继续叠加新流程。旧 CLI 与 Web E2E 行为保持兼容。
2. 首版契约族固定为 `general-e2e-contract-v1`。数据集内容版本、文件 schema、评分协议和软件版本分别记录，不能用一个“v1”替代全部版本身份。
3. 语义评分默认走 `codex-agent-judge-v1`，每题使用独立评分会话；`api-judge-v1` 只能由批次配置显式选择。任一后端失败均不得静默切换到另一个后端。
4. 报告的全集分母固定为 manifest 中的全部任务。执行失败、评测异常、有效评分和资源覆盖分别计数；评测系统失败不补零，也不从全集状态表中删除。
5. macOS 与 Windows 共享逻辑契约和 dataset digest，但平台能力分别验收。Windows 执行后跨机评分与 Windows 本机闭环是两个不同的支持声明。
6. 七个 General Skill 必须能单独分发；共享代码在构建时 vendoring 到各发行物，不要求安装者同时安装兄弟 Skill，也不依赖 WildClawBench checkout。
7. General E2E 的执行与评分不依赖 Docker。自动规则在专用虚拟环境的本地受管 Worker 中运行；独立进程和 runtime 副本用于复现与故障收口，不作为恶意代码安全沙箱。

## 2. 版本与标识符

### 2.1 契约和 schema 标识

所有结构化 JSON 文档必须同时携带 `schema_id` 和整数 `schema_version`。首版 `schema_version` 为 `1`，`schema_id` 固定如下；JSON Schema 文件名和 `$id` 在 G0-02/G0-03 中使用同一标识，禁止出现只有文件名相同但语义不同的副本。

| 对象 | `schema_id` | 首个实现任务 |
| --- | --- | --- |
| 数据集 manifest | `urn:wildclawbench:schema:general-e2e:dataset-manifest:v1` | G0-02 |
| 发行/分包 manifest | `urn:wildclawbench:schema:general-e2e:package-manifest:v1` | G1-04/G1-05 |
| 执行记录 | `urn:wildclawbench:schema:general-e2e:execution-record:v1` | G0-03 |
| 标准轨迹事件 | `urn:wildclawbench:schema:general-e2e:transcript-event:v1` | G0-03 |
| 轨迹索引 | `urn:wildclawbench:schema:general-e2e:trace-index:v1` | G0-03 |
| 资源指标 | `urn:wildclawbench:schema:general-e2e:resource-metrics:v1` | G0-03 |
| 单题评分 | `urn:wildclawbench:schema:general-e2e:score:v1` | G0-03 |
| submission | `urn:wildclawbench:schema:general-e2e:submission:v1` | G0-03 |
| 阶段回执 | `urn:wildclawbench:schema:general-e2e:receipt:v1` | G0-03 |
| release catalog | `urn:wildclawbench:schema:general-e2e:release-catalog:v1` | G1-05 |

首版读取器拒绝未知 major 版本。v1 内新增可选字段必须保持旧读取器可忽略、默认语义明确；删除字段、改变单位、改变枚举含义或把可空字段改为必填均需发布新的 schema major。数据集题目、Prompt、exec 或私有评分材料变化不靠 schema 版本表达，而是生成新的内容 digest；集合或题意发生有意变化时还需新的 dataset ID。

### 2.2 协议与软件版本

| 标识 | 含义 | 冻结规则 |
| --- | --- | --- |
| `general-e2e-contract-v1` | 跨阶段身份、状态、分包和报告语义 | breaking change 发布 v2 |
| `general-e2e-package-v1` | execution/scoring/return ZIP 的路径、安全和导入协议 | 分包边界变化发布新 major |
| `codex-agent-judge-v1` | Codex 独立评分会话的取证与逐 criterion 判定协议 | Prompt、证据策略或判定语义变化需新协议版本 |
| `api-judge-v1` | API Judge 的输入、输出、审计与失败语义 | 输入压缩或判定语义变化需新协议版本 |

评分模型、推理强度、Skill 版本、组件 SHA 和 source revision 是每次运行的冻结配置，不属于协议名称。相同协议但不同模型配置的结果不得无提示合并。

## 3. 目录和正式入口

首版目录名及职责锁定如下。目录迁移可以分任务实施，但不得在未更新契约和迁移说明时改名。

```text
eval_e2e/                          # 保留旧入口
eval_general_e2e/                  # General 仓库集成、数据集与 CLI
  datasets/
  adapters/
  cli.py
src/wildclawbench_grading_core/    # 可独立构建的规则、证据、语义后端和合分 core
tools/report/e2e-shared/           # 构建期共享源码，不作为公共 Skill 安装
  desktop-runtime/
  trace-adapters/
  resource-metrics/
  contracts/
  packaging/
  reporting/
tools/report/skills/web-e2e/       # 现有 Web Skill 源码分类
tools/report/skills/general-e2e/   # 七个 General Skill 源码分类
tools/e2e-build/                   # vendoring、依赖闭包、哈希与发行校验
tests/general_e2e/
```

七个 General Skill 的公开名称固定为：

- `prepare-general-e2e-workspaces`
- `execute-general-e2e`
- `collect-general-e2e`
- `orchestrate-general-e2e`
- `score-general-e2e`
- `report-general-e2e`
- `run-general-e2e`

评分 core 的首版公开能力名固定为 `run_rules()`、`build_evidence_index()`、`evaluate_semantics()` 和 `finalize_score()`。G3-01 已实现参数、返回值和 `GradingCoreError` 契约；G3-02 以 `grading-core 0.1.1` 装配到 `score-general-e2e 0.3.0/interface_only`，并交付不依赖 Docker 的私有评分 attempt 与本地受管规则 Worker；G3-03 交付 `orchestrate-general-e2e 0.2.0/interface_only` 的 Codex 项目注册和可恢复任务编排；G3-04 将两者升级为 `score-general-e2e 0.4.0/interface_only` 和 `orchestrate-general-e2e 0.3.0/interface_only`，交付 `codex-agent-judge-v1` 冻结证据、分页取证、逐 criterion 回传校验、三种 grading type 合分及 `verify-score` 准入；G3-05 再升级为 score `0.5.0/interface_only` 和 orchestrate `0.4.0/interface_only`，交付 Anthropic Messages、OpenAI Chat Completions、OpenAI Responses 三种 API transport、独立审计与可恢复 API 队列；G3-06 升级为 score `0.6.0/interface_only` 和 orchestrate `0.5.0/interface_only`，交付标准 submission、三类有效性分流及独立重评分 lineage。G4-01 将 `run-general-e2e` 升级为 `0.2.0/interface_only`，交付两级状态恢复、确定性 package、安全 import、幂等和冲突显式选择，并 vendoring 同一 `general-contracts` 校验器。core 本身仍不自行运行规则或调用模型；真实 Codex 小批、独立报告和完整生产闭环继续等待后续验收。

单元包的顶层目录固定为 `manifest.json`、`execution/`、`evidence/`、`receipts/`、`score/`、`.general-e2e/` 和 `submission.json`。运行时临时路径、日志文件名和内部缓存可以演进，但不能成为跨阶段身份的事实来源。

## 4. 身份、状态和恢复边界

- 逻辑执行身份由 `batch_id / unit_id / task_id / attempt_id` 组成；Harness 原生 thread、turn、session 和 cwd 绑定到 attempt，不替代逻辑身份。
- 阶段状态固定为 `NOT_SELECTED / PENDING / RUNNING / NEEDS_HUMAN / NEEDS_ATTENTION / COMPLETED / FAILED`。
- 执行业务终态固定为 `completed / candidate_error / timeout / infrastructure_error / cancelled`，与证据完整性和评分有效性分开记录。
- Prompt 发送意图和 Prompt digest 必须先持久化。恢复时只续原 attempt；无法确认是否已发送时进入 `NEEDS_ATTENTION`，不得以创建新任务规避不确定性。
- 评分重跑复用冻结候选并生成新的评分 attempt。不同执行 attempt 或评分 attempt 不能覆盖旧证据。

## 5. 评分与异常分母

### 5.1 默认与可选裁判

`codex-agent-judge-v1` 是含语义 criterion 任务的默认后端。评分会话逐题隔离，冻结模型、推理强度、Prompt digest、证据读取策略、预算和重试策略；评分输出必须引用可定位证据并保留未判定状态。

`api-judge-v1` 由批次配置显式启用，记录 requested/returned model、请求响应审计和 usage。API 失败产生该后端的失败终态；如需改用 Codex Agent，必须创建新的评分配置和 attempt，并保留原失败记录。

纯 automated 任务不因语义后端缺少配置而被阻止。自动规则与语义结果都先过确定性校验，再按原任务权重合分；Agent 无权修改 criterion、允许分值或权重。

### 5.2 分母与零值

报告至少同时给出以下互不替代的计数：

| 口径 | 定义 |
| --- | --- |
| `manifest_task_count` | 冻结 manifest 的全部任务数，批次中保持不变 |
| `execution_terminal_count` | 取得可信执行业务终态的任务数 |
| `valid_score_count` | 按契约得到有效总分的任务数 |
| `evaluation_error_count` | 因评测系统、证据或裁判失败而无法形成有效总分的任务数 |
| `unscored_count` | 尚未评分或评分未终态的任务数 |
| `metric_coverage` | 各资源字段自己的有效覆盖数/全集分母 |

`candidate_error` 或 `timeout` 在候选和证据足以按原规则评分时可以形成有效能力分；`infrastructure_error`、缺失必要证据或 Judge 服务失败不得冒充能力零分。能力均值以 `valid_score_count` 为分母，同时展示全集状态；跨批比较使用共同有效任务并披露交集大小。兼容旧 CLI 的“异常按零计”视图若确有需要，只能作为另一个明确命名的统计，不能覆盖主口径。

资源真实零值为数值 `0`；不可取得、未验证或被遮蔽的值为 `null`，并带来源状态。字段覆盖不完整时只展示已知小计和覆盖数，不把缺失值补零。

G3-06 已实现这一决策：标准 submission 对每个冻结任务显式写入 `valid / evaluation_error / unscored`，只有 `valid` 才进入能力分母；`total_score=0.0` 仍是有效能力分，Judge/证据失败保持 null，执行不可信或缺失必要证据不创建评分 attempt。重评分必须从已锁定 submission 派生新的 orchestration 和 attempt，并以 lineage 锁定源候选、manifest 与 score，不能覆盖原结果。

G4-02 已把该决策落实到独立报告：主均值只读取已校验 `valid` 分数，`evaluation_error/unscored` 在全集和分组中显式计数；CLI 适配也保留 null 和状态，不提供“异常按零计”的默认字段。资源指标以任务运行数为报告分母，同时保留采集文件内的原生观察覆盖；只有任务运行全集完整时才给 `total`，否则仅给 `known_subtotal` 和覆盖。裁判结果按 protocol、model、reasoning effort 分组，自动规则任务单独为 `not-required`。

## 6. 跨平台边界

- macOS 是首个实现和真实闭环基线；Windows 在相同 contract major 和 dataset digest 上适配，但验证结果单独登记。
- manifest、ZIP 和结构化记录中的逻辑相对路径统一使用 `/`；adapter 负责本机路径转换，同时保留原始路径和规范化路径。逻辑身份不依赖绝对路径或 basename。
- General 回传 ZIP 的 package ID 由逻辑身份、上游 manifest/receipt/submission SHA 和逐成员清单共同计算；ZIP 使用固定时间、权限、顺序和存储方式。导入目标按 `unit-id/package-id` 隔离，同 SHA 幂等，同逻辑身份不同内容必须并存并清空选择，不能以文件时间或“最新目录”自动裁决。
- Windows 的命令、路径长度、编码、CRLF、SQLite 锁、本地评分虚拟环境和进程树清理条件通过环境探针和 adapter 处理。若必须改变题意或 Prompt，发布可辨识数据集变体，不能沿用原 digest。
- “Windows 执行→macOS 评分”只证明跨机交接；只有 Windows 本机受管规则 Worker、Codex/API 评分、报告和恢复分别通过后，才能声明对应范围的 Windows 本机闭环。
- 任一平台的 PASS 只适用于记录的 OS/架构、Harness、模型、依赖和发行 SHA，不自动外推到另一平台或版本。

## 7. 独立发行与安全边界

- dataset bundle 是管理员准备输入；execution 包只包含 Prompt、初始 Workspace、最小 manifest 及执行说明，不能包含 GT、私有 rubric、评分脚本或评分凭据。
- scoring 包在执行终态后进入独立评分目录。候选原件只读保存；规则在一次性 runtime 副本中通过专用虚拟环境的本地 Worker 执行，GT 后置进入 private 区域。
- 单 Skill ZIP 包含自身运行所需的 vendored 组件、锁文件和 `bundled-components.json`。运行时不得 import 兄弟 Skill 私有模块、引用源码符号链接或读取仓库绝对路径。
- suite ZIP 只是七个独立 Skill ZIP 和 release catalog 的集合，不改变单 Skill 的独立性。
- 普通发行承诺“不依赖 checkout”且 General E2E 不要求 Docker；它不承诺完全离线，也不承诺宿主机无需 Node、Python 或网络。依赖和支持矩阵必须随包声明；完全离线发行另立版本和验收。
- 报告 Skill vendoring General contract validator，但不 vendoring Node 与 `@oai/artifact-tool`。XLSX runtime 必须通过显式参数或环境变量注入；报告器在临时目录建立运行时链接，产物全量验证后才原子发布。Windows junction 路径属于已实现代码路径，仍须 G5 真机验证。
- Web E2E 与 General E2E 可以携带不同的共享组件版本。General 目录迁移或组件抽取必须先通过受影响 Web 回归，不能用 General 测试替代。

## 8. 运行配置冻结进度

本节保留 ADR 接受时的运行配置边界。配置只有在真实实施节点取得证据后才能冻结；它们不阻止契约和数据集代码实现。

- Codex 评分模型和推理强度的具体值；
- Windows 版本、机器、本地评分运行时和客户端条件；
- API Judge endpoint、模型、凭据来源和输出预算；
- Windows 侧评分依赖锁/浏览器制品 digest 和 Artifact Tool runtime 实际路径；
- 12–18 题裁判校准样本的完整清单；该清单不再作为进入 Windows 真机适配前的执行门槛。

这些配置必须在对应首次运行前写入批次配置或验收记录。无法回读的值标为 `unknown` 或 `unverified`，不能用 UI 显示名推断不可变版本。

G2-01 已在不发送 Prompt 的前提下冻结当前 macOS 客户端配置：macOS `26.6.2/x86_64`、AStudio `3.3.1`、UI 模型 `GLM-5.2`、推理强度 `High`、权限“完全访问”、loopback CDP `9240` 和初始并发 1。证据见[探针结果](evidence/g2-01/astronstudio-macos-probe-2026-09-17.json)及[冻结运行配置](evidence/g2-01/astronstudio-macos-run-config-2026-09-17.json)。UI 显示名不能证明服务端不可变模型版本，因此该值继续记为 `unknown`；G2-02 发送前仍须精确回读当前配置。
