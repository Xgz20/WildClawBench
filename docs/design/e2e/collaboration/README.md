# macOS / Windows E2E 协作台账

两台机器通过 Git 同步代码、任务状态和交接要求。**每次接手先读本台账，处理发给本平台的交接，再推进任务卡的下一项；每次交付把代码、证据索引和接收方要做的事一起交接。** 不依赖另一任务的聊天记录，也不把“拉到最新代码”当作“本平台已验收”。

本目录是人工维护的协作台账，不会自动同步 Git、创建任务、安排桌面锁或持续监控。是否已发布基线以公共基线为准；任务派发/绑定见[派发记录](dispatch.md)，平台进展见各任务卡最近集成的快照；已有场景验收结论按其实际 revision 保留。

## 1. 唯一入口与任务索引

先读 [公共基线](baseline.md)，再读自己的任务卡和 [交接记录](handoffs/README.md)。表中只维护任务归属与链接，滚动状态写在对应任务卡，避免再复制一张容易过期的大表。

首轮接口批次、文件归属、正式收口依赖和桌面调度遵守 [并行实施边界](implementation-boundaries.md)。新建任务先完成独立开发和只读盘点，再由控制任务安排真机时段。

| COMMON | 契约、共享接口/指标、集成协调与基线发布 | 本 macOS 控制任务；公共代码实现可另指定唯一负责人 | [COMMON](tasks/COMMON.md) |

资料职责如下：

- [Harness 接入契约](../端到端自动化评测Harness接入契约.md)：跨场景要求和验收原则。

- `handoffs/`：每批变更对其他任务的影响及必需动作。接收结果由各接收方写进自己的任务卡，发送方不代填。

## 2. 两台机器如何同步

### 开始或恢复工作

1. **检查本机现场。** 记录当前项目、worktree、分支、HEAD、dirty 状态和仍活动的评测/Worker。Git 不包含本机运行状态；有未收口任务时先按原 attempt 处理，不能拉新 Skill 后继续旧批次。
2. **检查同步来源。** 从公共基线读取约定远端仓库和集成分支。两台机器的 remote 别名可以不同，但实际仓库须一致；不能默认两边 `origin` 指向同一个仓库，也不能只 pull 各自开发分支。
3. **获取公共分支和台账。** 在已获同步授权范围内 fetch，并把远端集成分支此刻的完整 SHA 固定为本轮 `SYNC_SHA`，后续按这个固定提交读取。主项目有其他活动工作时，不切分支、不改其文件，可先用 `git show <SYNC_SHA>:<path>` 读取台账。空闲且干净的集成检出才 fast-forward；自己的开发 worktree 用 merge 接入审查后的集成提交，不自动 reset、stash、rebase 或 force push。
4. **核对依赖与交接。** 读取本任务卡，扫描全部目标含本任务 ID 或 `ALL` 的正式交接记录，与任务卡“接收记录”按 ID 对账。未读、已读未接入、已接入未验证分别处理；不要只按文件时间或上次看到的最大编号推断没有漏项。
5. **更新本地代码。** 确认 `SYNC_SHA` 包含推荐源码基线、required commits 和本轮交接记录；推荐基线之后的额外提交也要完成影响审查。新 worktree 从核验后的 `SYNC_SHA` 创建，已有 worktree 合入它，分别记录推荐源码基线、已读台账的 `SYNC_SHA` 和实际工作 HEAD。只 checkout 较早的源码 SHA 可能缺少后续交接，不能据此判定没有新要求。merge 冲突按第 5 节处理，不能为继续工作抹掉另一平台的结果。
6. **确定本轮下一项。** 依赖满足则执行任务卡中的下一项；依赖未满足则执行已列出的独立工作。读取对应 Skill、配置和真实运行状态后再操作客户端。开始实际开发时更新 owner、任务 ID、worktree 和 adopted baseline，离开时更新恢复信息。

在不同操作系统上，证据路径、安装目录、客户端版本、登录态、CDP 和桌面权限都要本机核验；另一台机器的绝对路径只作为来源说明。主项目根目录的 `.agents/` 只存开发 worktree；调试和完整真机产物使用独立本地目录。

### 形成可交付进展

1. 更新自己负责的细项验收记录和任务卡：完成项、未完成项、测试证据、仍活动的运行、下一项。未取得目标平台证据不提升其状态。
2. 在 `handoffs/` 新建一份交接记录，写明修改内容、代码提交、目标任务、兼容性/旧证据影响、每个接收方的确切动作和验收条件。平台专属修改也要明确其他平台是否需回归；不需要时写依据。
3. 获准提交/push 时，按原有权限范围发布开发分支。**开发分支已 push 只表示可审阅；合入约定集成分支并推送后，才算另一平台常规同步可获取。** 未获远端写入授权时完成本地材料并保留“未发布”，不伪造已同步状态。
4. 集成负责人检查依赖、受影响回归和证据范围，合入代码及交接；在公共基线登记新的可消费 revision。跨平台真机尚未完成的验证明确列为待接收，不必让无关开发等待。
5. 接收方下次同步后，在自己的任务卡追加交接 ID、已采用 revision、验证结果/证据和后续任务；按既有授权提交/push 这份接收记录。双方都能从 Git 看见处理结果，聊天提醒仅作补充。

Git 只同步已提交并发布的内容。完整日志与任务产物默认留在来源机器，代码库放必要脱敏 fixture、命令、结论、证据清单和 SHA；接收方确需大文件时，记录本地/离线传递方式与接收哈希，缺文件时标明待交接。不能用 Mac 独有的绝对路径作为 Windows 已具备的输入。

## 3. 状态含义与可继续条件

任务卡的工作状态使用 `PLANNED / ACTIVE / BLOCKED / DONE`。`BLOCKED` 必须有具体缺项、责任方和恢复条件；有独立工作可继续时不把整张卡标成 BLOCKED。`DONE` 只表示该卡声明范围的清单完成、必需验收有据、代码已集成且必需接收动作已闭环，不代表所有平台都支持。

另保留三个相互独立的维度：

| 字段 | 记录什么 | 不能推导什么 |
| --- | --- | --- |
| 代码交付 | `LOCAL_ONLY / BRANCH_PUBLISHED / INTEGRATED` 及对应提交 | INTEGRATED 不等于真机验证通过 |
| 验证引用 | 精确平台/版本、验收 ID、证据 revision；沿用理由或受影响项待复验 | macOS PASS 不等于 Windows PASS；旧版 PASS 不等于新基线 PASS |
| 交接接收 | `SEEN / ADOPTED / VERIFIED / BLOCKED / NOT_APPLICABLE`，附提交、证据或理由 | ADOPTED 只表示代码已采用，不能关闭必需回归 |

公共基线允许区分“开发可消费”和“平台已验收”。第一批并行任务的硬依赖是：macOS 最终修复收口、契约和最小公共适配/指标接口明确并集成。全部新增指标的实现不是硬依赖；任务卡应写出这一区别，避免 Windows 无谓等待，也避免各分支自创字段。

每份交接的接收动作分别标为：`REQUIRED_BEFORE_EXECUTION`（先验证才能运行受影响链路）、`REQUIRED_BEFORE_CLAIM`（允许开发，但通过前不能提升支持声明）、`INFORMATIONAL`（核对影响后记录即可）。没有适用修复或证据过期事项时，不因另一平台推送了无关文档就强制重跑整套 E2E。

## 4. 一次交接需要写清什么

使用 [交接模板](handoffs/TEMPLATE.md)，文件 ID 采用 `<来源任务ID>-<该任务内递增序号>`，例如 `WIN-ASTRONSTUDIO-GENERAL-001`。序号只在各任务内分配，避免多机抢全局编号；模板文件不算待处理交接。

至少包含：

- 来源任务、目标任务、变更目的、修改文件范围。
- base SHA、实现提交、必需依赖、目标集成分支与集成后的 commit 映射。
- Schema/状态机/CLI/配置/依赖/Skill 与包身份的变化，是否需要重建、重装或新建评测批次。
- 已验证范围和未验证范围；哪些旧证据需复验，哪些可沿用及原因。
- 接收方需要执行的**唯一或有序下一步**：入口/实际命令、前置配置、对应验收 ID、通过条件、失败时保留哪些现场。
- 可随 Git 获取的证据索引、仅本机存在的原件与哈希，以及需要另行交付的输入。

实现 commit 不能记录自身未知的 SHA：先形成实现/证据提交，再用后续交接提交引用它；这两个提交作为同批交付集成。不 amend/重写已公开历史来补自身 SHA。纯文档初始台账可以一个提交交付；公共基线也引用它之前已存在的源码提交。实际台账版本从 `git log` 读取，不手填自指 SHA。

通常保留原提交做 merge，依赖按祖先关系验证。若采用 squash/cherry-pick，集成负责人必须登记原实现 SHA → 集成 SHA 的映射并核对内容，接收方按集成 SHA 判断可用性；不能因原 SHA 不在历史中就重复应用，也不能只凭同名 commit 标题认定相同。

## 5. 避免清单与代码冲突

- 公共基线和任务索引由控制任务维护；每张任务卡由该任务的唯一负责人维护；每份交接正文由发送方维护。接收方只写自己的卡，减少多人编辑同一文件。
- General/Web 原验收清单按任务 ID、平台/Harness 行更新，保留失败历史。共享顶部总结由集成负责人根据各行结果更新；平台任务不得覆盖另一平台的证据或把全局“下一项”当作所有机器都必须做的唯一任务。
- 公共注册入口、Schema、指标公式、队列语义和构建装配由 COMMON 协调唯一实现负责人。平台任务提交具体需求、fixture 和影响清单；接口确定后独立开发。平台文件不等于绝对无共享影响，需审查调用方。
- 已在开发分支发布的任务卡声明不是分布式锁。同一任务不能两机同时认领；转交时原负责人落盘现场，控制任务登记新负责人，接收方确认后再写。未确认归属时可只读分析，不开始重叠修改。
- 文本冲突逐项合并：同一验收的不同 revision/平台结果保留为不同记录，不以时间较新者覆盖；生成文件从合并后的 canonical 源重建；公共语义冲突先协调，独立平台层继续。
- 桌面互斥由本机控制者/锁实现，不能用 Git 的状态行代替实时锁。macOS 三个 Harness 可并行写代码，但原生对话框、重启和 smoke 时段仍需协调；Windows 同理。

## 6. 两个平台反复使用的短 Prompt

在对应本地项目的新任务或恢复任务中使用；将任务 ID 选为本平台负责的一项，不需要粘贴历史聊天。此 Prompt 的 Git 读写以用户既有授权为准，不隐含合并或远端发布权限。

```text
继续本机 E2E 协作任务：<任务ID>。
先检查 Git/worktree 和本机活动运行，读取 docs/design/e2e/collaboration/README.md、baseline.md、本任务卡及发给本任务/ALL 的交接记录；在现有同步授权范围内获取约定集成分支的最新台账与代码。
核对已采用基线和必需提交，处理尚未接收/验证的交接，再直接执行本任务卡中满足依赖的下一项；缺依赖时继续卡片列出的独立工作。代码修改限于主项目 .agents/ 下的 feat/ 分支 worktree。不要覆盖旧 attempt，也不要把别的平台通过当作本机通过。
每阶段更新自己的任务卡、对应细项验收和证据索引；有跨任务影响时新增交接记录，接收时写回处理结果。提交/push 按本次或既有授权执行，未发布明确标注。除本机凭据、权限或真实阻塞外，不依赖聊天补充上下文。
```

例如，macOS 修改共享资源解析器后，交接指定 Windows 要做的 parser fixture、原生样本对账及受影响报告检查。Windows 拉取后先采用该提交、完成这些动作并回写结果，再进入自己的 G5 下一项；若发现 Windows 路径问题，则另发修复交接给 COMMON 和受影响的 macOS 任务。历史双方结论与下一步始终跟随代码保存。
