# 评测报告审核清单

## 自动对账

| 层级 | 检查内容 | 失败条件 |
|---|---|---|
| 文件结构 | 必需 Sheet、表头、详情 Sheet、unit 和任务集合 | 缺失、重复或范围不一致 |
| 总览 | 均分、用例数、完成/错误/超时、token、请求、耗时、成本、工具调用 | 无法从 raw 独立复算 |
| 状态约束 | 正常完成+执行错误+超时+评测异常=用例数，四类互斥 | 恒等式不成立 |
| 重跑选择 | `run_metadata.json.supersedes_run` 与有效 run 集合 | 被替换旧 run 仍参与均值、轮数或有效性结论 |
| 详情 | 每任务总分、状态、用量、耗时、工具调用和分析列 | 与最新 run/多轮均值不一致 |
| 维度 | 分类、难度、模态的集合、列头样本数、分组均值和总均分 | 元数据或重算不一致 |
| Agent 能力 | 7 维能力、去落盘污染能力与检查点映射 | 无法从 score 检查点独立复算 |
| 矩阵 | 模型×Harness 总分、unit×unit 分差 | 与 raw 总分不一致 |
| 上游门禁 | validity JSON 结论 | 上游 `FAIL` 直接阻断 |

## 反常识统计

以下现象默认只判 `REVIEW`，不能脱离证据宣称脚本错误：

1. 工具调用显著高于模型请求数：先核对 request 定义、流式事件和多工具并发，再检查旧版 Codex/AstronCode `request_count` 低估问题。
2. 难度倒挂：检查每档样本量、任务类型、评分方式和模型强项。多数 unit 同方向且分差显著时，优先审查难度标签和任务集构成。
3. 高难度方差反而更小：可能是大量稳定零分或门控短路，不应解释为模型更稳定。
4. token、请求、耗时或成本排名与得分排名完全相反：检查是否存在过早退出、循环不收敛、缓存、零成本供应商或用量解析差异。
5. 完成率高但得分低：正常退出不代表完成任务，重点抽查未落盘和过早结束。
6. 超时得分非零：超时前产物可能已被评分，不应自动视为口径错误。
7. 某模型所有任务分数高度离散在 0/1：检查评分门控、裁判失败和结果文件缺失。
8. 分类、模态或能力分显著偏离总分：按样本数做加权复算，检查缺失任务和未映射检查点。

## Excel 人工审核

1. 数字格式是否与值域一致：百分制单元格存 `0~100`，用例详情分数存 `0~1`，避免二次乘 100。
2. 排序和条件格式是否覆盖正确范围，最高/最低 unit、最佳单元和最大分差是否正确。
3. 多轮统计是否使用正确口径：任务内均值、标准差、pass@k 和 pass^k 不应跨题直接平均后解释。
4. 详情中的执行错误与超时是否互斥展示，裁判错误是否误写成模型错误。
5. 根因分析回填是否对应正确 `unit::task_id`；同 unit 的多个 scope 文件有重叠时是否记录覆盖顺序。
6. 工具成功率、格式准确率和不确定占比的分母是否一致，未知状态不能静默算作成功。

## Markdown 结论审核

1. 每个数字能否定位到 Excel Sheet/列/行，且 Excel 与原始结果已通过对账。
2. 总览排名、领先幅度、强项/短板、难度和模态结论是否与表格方向一致。
3. 是否把相关性写成因果，或用请求数、token 数直接证明模型能力。
4. 是否将共享环境、模型专属通道、harness、grader 和模型能力明确分层。
5. 典型案例是否引用真实 transcript、score 和判分代码；单个案例不能代表总体。
6. 是否披露缺失 unit、异常用例、补跑、重解析、筛选范围和未决 `REVIEW`。
7. 建议是否与证据对应，并区分修环境、修 runner、修 grader、重跑和改进模型。

## 发布标准

- `FAIL` 必须修复并重生成；不能只改报告措辞。
- `REVIEW` 必须逐项写人工结论、证据和接受风险的人；未闭环前不标 `PASS`。
- 自动 `PASS` 只代表机器对账未发现问题，仍需完成 Excel 与 Markdown 人工审核。
