# 执行异常与评分的统一边界

本政策为`evidence-accountability/v1`。新评分attempt显式冻结该Profile，适用于全部题目和Harness；不按题号建立豁免名单，不改历史attempt、原Rubric文本、权重或分值锚点。C1、C7等是各题Rubric中的检查点key，不同题目的含义可以不同。

## 先核对任务是否真正进入被测端

1. 核对原Prompt摘要、题目与执行身份、原生受理回执或turn/session、执行Workspace、发送状态；点击发送、排队或出现标题不等于原生受理。未知发送只观察原请求，不自动重发。
2. 核对公开题面、输入附件、GT/参考、必要工具定义和执行准备是否正确可用。题源缺必需材料、自动化没有送达题目、评测侧操作中断了任务，均属于评测框架/题源问题，不能算Harness能力0分。
3. 区分修复影响的阶段。影响题面、输入、派发或实际作答的框架修复后，重新执行该题并建立新执行attempt；旧attempt失效原因与原件保留。仅修复采集/评分端且能完整恢复原作答时，重新执行采集/独立评分阶段；不得改变原作答，也不得借修复自动重跑已受理的Harness失败。无法确认修复是否影响作答时才交用户决策。
4. 账户额度、登录、锁屏等评测前提未满足时先恢复条件，不将评测条件不足换成能力0；沿用相应原生恢复约束。

## 已受理后的Harness异常进入逐检查点评分

原生provider通信报错、工具桥报错、中断、超时、未产生产物、未产生轨迹或未提供行为证明，均不单独阻止评分。须有可绑定原执行的原生受理/失败事实和稳定原候选快照；候选可以是实际空目录，不能伪造成功或补造日志。

- 用全部已保留的原始过程、SDK前段、工具返回、答复和产物评价每个检查点，允许原Rubric规定的等价证据。不能丢掉已有证据凑0分。
- 被测端未提供该检查点要求的交付或行为证明，该项不得分；已有证据支持的工作仍按原锚点获得部分分或满分。整题0分是逐项评分及原聚合的结果，不是执行异常状态的固定映射。
- 无返回的调用不能推断执行成功；“没有足够证明满足检查点”也不等于断言未观察的行为绝对没有发生。后者仍要求完整无过滤轨迹覆盖。
- 原Rubric的“缺证不可判定”按证据归属解释：被测端未产生日志、未交付或未证明行为，按该检查点不得分；评测侧没有采到、丢失/损坏原证据、解析失败或题源缺少必要参照，先修复，不能冒充候选0分。缺少真实工具schema不是候选参数错误的证明。
- 根因归属研发尚未闭环不单独阻断已有材料的检查点评分；已证实评测框架/题源污染了执行的，返回前一阶段修复，不混入候选成绩。

## 代码准入及证据交接

`assess-execution --unit-root ABS --execution-record ABS`只读核验并输出处理建议，不创建分数或发送请求。`status=PASS`表示诊断命令成功，不表示任务成功或已评分；以`disposition`区分原作答评分、执行前修复、前提恢复和待决。

`prepare`不再要求失败题命中特定contract白名单：已有`verified-failed-output-evidence/v1`证明的AStudio原生错误，在重新核验原Prompt、原始状态、原生会话、原错误、证据清单及候选摘要后，使用`verified-harness-failure-evidence/v1`准入；不要求SDK终态存在。已有完整原生中断证明通过`verified-harness-interruption-evidence/v1`准入，不再逐题索取评分授权。身份、文件摘要和候选只读保护不放宽，原FAILED/partial/unavailable状态保持。

旧采集没有另存failure-proof时，可从原执行记录旁的正式evidence-manifest中绑定唯一原automation-state，核验原Prompt字节、完整原生会话身份、一次发送、FAILED及一致的原生TURN_ERROR/TURN_FAILED；在新评分目录冻结派生证明，不改旧执行记录。会话native_status可能是上次轮询遗留的running，不能覆盖已绑定的原生错误事实；该字段原值仍留档。普通框架超时、未知错误或仅候选自述不属于该证明。

所有仍存在的SDK前段、原生消息和原文件必须纳入本次采集/评分证据；不能因为标准轨迹没有收口而丢弃原始材料。当前其他适配器若没有可核验的失败证明，先实现/修复该适配器的证明交接；不能仅信任错误字符串，更不能以“不支持证明”判候选0分。原生根因调查与评分分开留档。

取证器将“候选未提供正式答复/产物”误抛为评测缺证时，应交接明确未提供状态，仍由原数值规则和独立裁判评分。只修复证据表示，不造完成事件或回执，不返回框架预设的全题分数。未知取证器异常必须附具体函数、错误、输入摘要和影响的检查点，不能伪装候选缺失。

## 仅在前述规则仍无法决定时交用户决策

语义响应仍可使用`unresolved/score=null`，但每个这样的检查点必须对应`decision_requests`中的一项，且origin只能为`evaluator`、`task_source`或`unresolved_origin`。被测端没有证明满足检查点不能作为unresolved的理由。

独立能力项的`evidence_insufficient/blocked_external/not_observed/evaluator_error`同样逐key列入决策请求，不能因业务总分有效而遗漏；运行有效性缺证使用`criterion_key=run_validity`。已完整核验仅有被测端未满足要求的能力，应按原锚点填写有效fail/0，而非not_observed空值。确实缺必要参照或运行污染证明未能核实时，仍保留具体未决问题。

每项必须填写：`criterion_key`、`origin`、`problem`、`missing_evidence`、`evidence_checked`、`why_rules_cannot_decide`、`repair_execution_impact`、非空`proposed_actions`和`decision_question`。问题应包含原件路径/行号、哪些事实已确认、哪些不能确认、是否需要重执行、保留原作答能否修复，以及具体需要用户选择的处理。不得只写“缺证”“根因不明”或“是否授权评分”。

`evidence_checked`可为非空文字或非空文字列表，便于逐条保留已核查材料；其他上述说明字段为非空文字，`proposed_actions`为非空文字列表。该字段只记录审计说明，允许列表表示不改变任何判分。已经锁定的旧协议错误不原地修补，应由新attempt重新独立评分。

报告区分执行异常与评分有效性。正式0分计入有效评分；评测框架/题源问题或确实未决项保持null，披露范围和原因，不补零、不删项重归一化。旧结果不原地改写；需要修复/重评时使用新attempt并显式选择来源。
